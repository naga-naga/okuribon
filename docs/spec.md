# おくりぼん — デザイン仕様

この文書は規範だけを書く。実装を縛る決まりと、それを短く支える理由までを持ち、
判断の経緯や却下した代替案は `docs/decisions/` に1件1ファイルで積む（decisions/0001）。
節番号はコード内のコメントと skill から参照されているため動かさない。

## 1. このツールは何か

顔見知りの少人数グループが、電子書籍を持ち寄って交換し合うための Web ツール。

**サービス名は「おくりぼん」。** 贈る＋本から採った。画面と文書はかなで書き、ローマ字の `okuribon` は識別子（リポジトリ名、Kamal の service 名、DB 名、サブドメイン）にだけ使う。Ruby の命名がそう要求する `Okuribon`（`config/application.rb` のモジュール名）を除き、**利用者の目に入る場所にローマ字を出さない。** 画面にかなとローマ字が並ぶことはない。

名前を書く場所は `config/locales/ja.yml` の `service.name` 1つに絞る。ビューは `t('service.name')` で引く。アプリのレイアウトを通らない `public/500.html` と `public/406-unsupported-browser.html` だけは直に持つが（6.10）、食い違わないことを spec で押さえる。以前は「読書交換会」と「Okuribon」が画面ごとに別々に書かれており、片方だけ直した状態に気付けなかった。

一般名詞の「交換会」は、この道具そのものではなく1回のイベントを指す（2.）。サービス名に「読書交換会」を採らないのはこのため。画面には「冬の読書交換会 2026」のような交換会名が常に出るので、同じ語を道具の名前にすると、どちらの話かを読み分けることになる。

主催者が「交換会」を作り、参加者はそこへ自分のおすすめの本を登録する。全員が登録し終えたら、それぞれが欲しい本の希望順を提出する。締切後にマッチングが実行され、誰がどの本を受け取るかが決まる。受け取った本のギフトコードが開示され、各自が自分でストアで受け取る。

招待された人だけが参加する。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 交換会 | 一回の交換イベント。すべての単位となるリソース |
| 主催者 | 交換会を作った人。必ず参加者を兼ねる |
| 参加者 | 交換会に招待され、参加した人 |
| 本 | 参加者が提供する電子書籍。1人が何冊でも登録できる |
| ギフトコード | 電子書籍をギフト購入した際に得られる文字列。これを渡すことで本が贈られる |
| 取得枠 | その人が受け取れる冊数。自分が登録した冊数と同じ |
| 希望リスト | 欲しい本を希望順に並べたもの。順序が意味を持つ |
| マッチング | 希望リストをもとに、誰がどの本を受け取るかを決める処理 |
| 返却 | 誰にも渡せなかった本が、登録した本人に戻ること |

## 3. 交換の仕組み

デザイン上、参加者に理解してもらう必要がある要点のみ。

- **登録した冊数だけ受け取れる。** 3冊登録した人は3冊受け取る。1冊も登録しなかった人は受け取れない。
- **自分が登録した本は受け取れない。**
- **マッチングはスネークドラフト方式。** 参加者をランダムに並べ、順に希望リストの最上位から1冊ずつ確保する。次の巡では順序が逆になる。これを取得枠が埋まるまで繰り返す。
- **希望リストは長いほうが有利。** 上位が他の人に取られると、下位へ順に降りていくため。取得枠の2倍以上を推奨として案内する。
- **希望を出さなかった人**は、最後に余った本がランダムに割り当てられる。受け取る権利は失わない。
- **マッチングは一度だけ実行される。** 抽選に使う乱数シードは交換会の作成時に固定してあり、実行時には生成しない。同じ結果を作り直すことはできない。

## 4. フェーズ

交換会は以下のフェーズを順に進む。フェーズは日時から自動で判定される（マッチング実行のみ主催者の操作）。すべて JST。

| フェーズ | 参加者ができること |
|---|---|
| 準備中 | 招待URLから参加する。本の登録はまだできない |
| 登録期間 | 本の登録・編集・削除。他の人が登録した本も一覧で見られる |
| 希望提出期間 | 希望リストの作成・並べ替え。本の追加や編集はできない |
| マッチング実行待ち | 何もできない。結果を待つ表示のみ |
| 結果公開 | 自分が受け取った本とギフトコードを確認する |

補足：

- 登録期間の終了と希望提出期間の開始は同時刻とする。重ならず、かつ間も空けない。間を空けると、どのフェーズにも属さない時間が生まれてしまうため。希望提出期間の開始は独立した項目として持たず、登録期間の終了から導出する。
- マッチングは主催者がボタンを押して実行する。自動実行ではない。
- 結果公開かどうかは、マッチング実行日時が入っているかどうかだけで決まる。実行後に主催者が各期間の日時を過去や未来へ動かしても、結果公開のままになる。
- 主催者は各期間の日時を後から変更できる。
- 参加できるのは登録期間の締切まで。
- 参加の辞退も、主催者による参加者の除外も、登録期間の締切まで。希望提出期間に入ってから抜けられると、取得枠の計算が壊れるため。
- 主催者は自分の交換会から抜けられない。辞退もできず、自分自身を除外することもできない。抜けられる期間かどうかによらない。
- 辞退すると参加の記録は残さず消す。登録した本もあわせて消える。抜けた人の本が残ると、誰も受け取れない本として一覧に並び続けるため。辞退した人は、登録期間のうちなら同じ招待URLから参加し直せる。
- 各期間は開始時刻を含み、終了時刻を含まない。締切ちょうどの時刻は、その期間の外になる。
- 書き込みの可否はサーバー側で検証する。リクエストで送られたフェーズや時刻は使わない。読み取りは全フェーズで開いており、書き込みだけを止める。

## 5. 画面一覧

**未認証**

1. ログイン画面
2. 招待URL着地画面

**参加者**

3. 交換会一覧
4. 交換会ページ（状態ヘッダー ＋ 本の一覧 ＋ 希望リスト編集） ← 最重要
5. 本の登録・編集フォーム
6. 結果画面

**主催者**

7. 交換会の作成・編集
8. 主催者管理画面

1冊だけを開く画面は持たない。理由は 6.3。

**サービストップも持たない。未認証の着地はログイン画面とする。** 未ログインでトップページを開いた人はログイン画面へ送られ、認証を終えると交換会一覧へ戻る（6.6）。この道具は招待された人だけが参加する（1.）。招待された人は招待URLから来て、着地画面が交換会名・概要・主催者・日程を見せる（6.7）。サービストップに来るのは招待URLを持たず、名前だけを知って訪れた人にあたる。

その人に返せるものは2つしかなく、どちらも既に置き場所がある。「招待URLを開いてください」はログイン画面が見出しの下の一文で言い、「主催するなら自分でつくれます」は交換会一覧の空状態が、主催するときの目安と交換会をつくるボタンごと引き受けている（6.6）。認証の前にも置くと、同じ説明が2か所になる。片方だけが古い言い方で残る。

加えて、名前を画面に大きく出すのはログイン画面の見出しだけと決めている（下）。サービストップを置くと名前を大きく出す画面が2枚並び、どちらがこの道具の入口なのかが決まらない。**この判断が乗っている前提は、招待URLを持たない人がここへ来る道が無いこと。** 前提が崩れるのは、招待の外から人が訪れる経路ができたとき。名前だけを知って来る人が現れる形になったら、そのとき何を返すのかから決め直す。

**交換会の中を1枚に畳んである。** 交換会を開くと本が並んでいて、その上に現在の状態が載っている。状態だけを見せる交換会トップは持たない。要件は上半分（状態ヘッダー）を 6.1、下半分（カードと希望リスト）を 6.2 に分けて書くが、画面は1つ。判断の経緯は `decisions/0012`。

エラー画面はこの一覧に入れない。利用者が目指して開く画面ではなく、どの画面からでも起きうる応答のため。要件は 6.10。

ログイン画面を除く全画面に共通ヘッダーを置く。左は現在地までの祖先を連ねたパンくず、右はログイン中の利用者とログアウト。現在地はパンくずに入れない。画面の名前は h1 にある。交換会の中で画面をまたぐタブは持たない。行き先を並べるのは交換会ページの状態ヘッダーの仕事（6.1）で、共通ヘッダーにも並べると同じ導線が2か所になるため。

**パンくずの根は「交換会一覧」と名乗る。** サービス名ではない。根が指す行き先は交換会一覧（6.6）なので、そこを名前にすると全段が「画面の名前」で揃う。サービス名を置くと、根だけが行き先と一致しない。**ログイン後にサービス名を出す場所は持たない。** 名前が画面に大きく出るのはログイン画面の見出しだけで、その先は、どの交換会に居るかのほうが要る。

交換会一覧そのものを開いているときは、根が現在地にあたる。リンクにはせず `aria-current="page"` を付ける。祖先だけを連ねるという上の規則の唯一の例外で、根を消すと共通ヘッダーの左が空になる。この画面の h1 は「あなたの交換会」（1つも参加していないときは「まだどこにも参加していません」）で、根の「交換会一覧」と語が重ならない。

**未ログインのときだけ、根はサービス名を名乗る。** 交換会一覧はログインしないと開けず、未ログインの人にとって祖先にあたらない。行き先にならない画面の名前を置いても読む用がない。該当するのは招待URL着地画面（6.7）だけで、招待された人がこの道具の名前を最初に見る場所でもある。リンクにはせず、現在地でもないので `aria-current` も付けない。

## 6. 各画面の要件

### 6.1 交換会ページ — 状態ヘッダー（最重要）

参加者が最も頻繁に訪れる画面。数週間にわたって断続的に訪れるため、久しぶりに開いても迷わないことが最優先。

**交換会を開くと本が並んでいる。** 状態だけを見せる交換会トップは持たない。参加者がこのツールで時間を使うのは本を読み比べているときで、状態だけの画面はそこへ向かう途中の通過点にしかならない（`decisions/0012`）。

この節はページの上半分にあたる**状態ヘッダー**を書く。下半分のカードと希望リストは 6.2。分けて書くのは要件の量のためで、画面は1つ。

必ず一目で分かるべき3点：

1. **今どのフェーズか**
2. **締切まであとどれくらいか**（残り日数・時間）
3. **自分は今なにをすべきか**（例：「あと2冊登録できます」「希望リストがまだ空です」）

そのほかに載せる情報：

- 交換会の名前と主催者名、参加者数
- 交換会の概要（対応ストア、価格帯の目安などが自由記述で書かれている）と日程
- 登録された本の総数
- 自分が登録した本の冊数 ＝ 自分の取得枠
- 各画面への導線

フェーズごとに5つの状態がある。それぞれ「すべきこと」が変わるので、5パターン必要。

- 準備中：登録期間の開始を待っている
- 登録期間：本を登録する
- 希望提出期間：希望リストを作る
- マッチング実行待ち：待つだけ
- 結果公開：結果を見る

#### 並び

最上段にフェーズ帯を置き、その下を左右2つに割る。左は「あなたがすること」と、その日の操作。右は締切と状況の数字。フェーズが変わっても、どちらに何があるかを動かさない。数週間ぶりに開いても、目の置き場所を覚え直さずに済むことを優先する。

**フェーズ帯は5つのフェーズを順に並べ、現在地に印を付ける。** 現在のフェーズ名だけを出すと、それが5つのうちのどこなのか、次に何が来るのかが読み取れない。数週間かかるツールで、参加者が全体の道のりを覚えている前提は置けない。

ただし**押せるものに見せない。** フェーズは日時から導出されるもので（4.）、選べる先ではない。タブの形に寄せると押せると読まれるので、現在地以外は生成りに沈めた道のりとして描き、リンクにも button にもしない。

**導線は「あなたがすること」の直下に置き、独立した段を作らない。** その日の主な行き先は本の一覧で、それがページの下半分そのものにあたる。段に残るのは操作（本を登録する、マッチングを実行する、結果を見る）で、これは「すること」の一部にあたる（`decisions/0012`）。することを書いた真下に押すものがあるほうが、間に締切や数字を挟むより短く読める。

**操作の位置と大きさは行き先で分けない。** どのフェーズでもそこに出るものが、その日の主となる導線にあたる。フェーズごとに強さを変えると、押すものの見つけ方をフェーズの数だけ覚えることになる。

押せる期間は書き込みの可否から引き、フェーズ名で条件を書き直さない。押しても断られるボタンが、どこかのフェーズに残るため。書き込みが閉じているフェーズでは、押せないボタンを残す代わりに、いつから押せるのかを書く（「本の登録は2月1日から」）。ボタンが消えたことを不具合と読ませないため。

#### 3点がカードに埋もれないこと

状態ヘッダーの下には十数枚のカードが続く。**スクロールすると状態ヘッダーは高さ52px程度の帯に畳まれ、上部に残る。** 帯に残すのは交換会名・フェーズ・すべきことの見出し・締切までの残り、および希望提出期間なら希望の冊数と取得枠。読み進めても3点が視界から出ない。

**狭い画面では、帯から希望の冊数と取得枠を落とす。** 下部に固定した希望リストのシートが同じ数を1行で持っており（6.2）、上と下で同じ数字を挟むことになる。落とすのは帯のほうとする。シートの数は畳んだ状態でも常に出ていて、順位付きのチップと並んでいるぶん読み取れるものが多い。

**狭い画面では交換会名も落とす。** 375px では「マッチング実行待ち」のチップだけで幅の3分の1を取り、交換会名・フェーズ・すべきこと・残りの4つは1行に入らない。落とす順は3点に入らないものからとし、交換会名が先になる。どの交換会を開いているかは、1つ上へ戻れば状態ヘッダーが言う。

**残り時間を持たないフェーズ（マッチング実行待ち・結果公開）は、帯の右端に何も出さない。** 状態ヘッダーのほうは締切の枠を空けないが（下記）、それはラベルの付いた枠が空欄になると、締切を見落としたのか無いのかを読み分けられないため。帯はラベル付きの枠を持たない1行なので、空欄に見える先がない。

**畳みは JavaScript が動いてから効く。** 帯は最初から描いておき、状態ヘッダーが画面の上へ出たかどうかで隠す・出すだけを切り替える。動かない環境では帯が出ないまま状態ヘッダーが流れる。判定はスクロール量ではなく状態ヘッダーとの交差で持つ。高さがフェーズと概要の長さで変わるので、しきい値を px で置くとどこかのフェーズでずれる。

帯は本文の上に重ねて上部へ固定する。共通ヘッダーは現行のまま流す（`decisions/0006`）。畳むのは状態ヘッダーが上へ出てからで、その時点で共通ヘッダーは先に流れている。

状態ヘッダーそのものの高さは、開いた直後に本のカードが1行ぶん見えるところまでに抑える。全部を占めると、開くたびに状態を読ませてからでないと本に辿り着けず、統合した意味が無くなる。

**概要と日程は常設する。ただし状態ヘッダーの外に置く。** 畳んで格納しても、畳んだ枠が1行ぶんの面を取るので節約できる高さは変わらない。対応ストアや価格帯を読みたいのは「本を登録する」を押す直前で、そこに1クリック挟むほうが重い（`decisions/0006`）。フェーズごとの出し分けも持たない。準備中だけを例外にする理由が無くなる。

外に置くのは、概要が自由記述で長さに上限を持たないため。状態ヘッダーの中に入れると、主催者が長く書いた交換会でだけ締切と状況の数字が下がり、位置を動かさない決めごとが概要の長さで崩れる。

#### あなたがすること

フェーズだけでは決まらない。同じ登録期間でも、1冊も登録していない人とすでに登録した人では次にすることが変わるため、取得枠・希望冊数・受け取った冊数を見て文言を選ぶ。組み立てはビューではなくサービス（`Exchanges::Todo`）に置く。交換会一覧のカード（6.6）も同じ一文を並べるので、2か所で別々に組むと片方だけが古い言い方で残る。

**フェーズだけで決まる一文を別に持たない。** 同じページに2つの「次にすること」が縦に並ぶことになるうえ、片方は本人の状態を見ず、もう片方は見るので、言うことが食い違いうる。`Exchanges::Todo` に一本化する（`decisions/0012`）。

**マッチング実行待ちだけは、主催者かどうかでも変わる。** ほかのフェーズで次に何が起きるかを決めるのは日時か本人の操作だが、このフェーズを動かせるのは主催者の実行だけにあたる。全員に「結果を待ちます」と書くと、押す当人にまで待てと言うことになり、交換会がそこで止まったままになる。主催者には「マッチングを実行する」を出し、押さないあいだ参加者が結果を見られないことを添える。取得枠・希望冊数・受け取った冊数のほかに役割まで見るフェーズは、5つの中でここしかない。

主催者かどうかは実行の可否（`Exchange#matching_executable?`）から引き、フェーズ名で書き直さない。確認画面（6.8）が開く条件と別々に書くと、押しても断られる導線がこの画面に残る。実行済みで導線が消えるのも同じ判定に乗る。マッチングは一度だけ実行できるため（3.）。

**実行への導線は主催者管理画面を経由せず、実行の確認画面（6.8）へ直接送る。** 押す前に何人に何冊が渡るのかを数で示すのは確認画面の仕事なので、間に管理画面を挟んでも増えるものが無い。確認画面へ入る経路は管理画面と合わせて2本になるが、どちらも同じ述語で可否を決めており、取り返しのつかない操作の手前に確認が挟まることも変わらない。管理画面へ辿り着く経路が交換会ページだけであること（6.8）にも影響しない。

希望提出期間に取得枠が0の人には、希望リストを促さない。その時点で登録期間は終わっており、取得枠を増やす道が残っていない。受け取れないことだけを伝える（6.2 の冊数の案内と同じ扱い）。

#### 締切と状況の数字

締切の数え方は「締切まであとどれくらいか」を、数えられるいちばん大きい単位ひとつだけで出す。1日以上なら日、1日未満なら時間、1時間未満なら分。端数は切り捨てる。切り上げると、1日を切ってからも「あと1日」と出続けて、締切が近づいていることが表示に現れない。1分を割ったら数えるのをやめて「まもなく」とする。秒は毎秒変わるのに画面は更新されず、止まった数字を見せることになるため。

「次の締切」がどの日時を指すかは 6.6 と同じ。**マッチング実行待ちと結果公開には残り時間が無いが、枠は空けない。** 実行待ちは「締切：ありません」と書き、することがもう無いことを添える。空欄にすると、締切を見落としたのか、そもそも無いのかが読み取れない（6.6 と同じ理由）。結果公開は締切の枠を、公開日時と結果画面への入口に差し替える。

状況の数字は3つ並べる。**枠の位置は動かさず、中身はフェーズで入れ替える。**

| フェーズ | 3つの数字 |
| --- | --- |
| 準備中 | 参加者 ／ 本（0冊） ／ 取得枠（—） |
| 登録期間 | 参加者 ／ 本 ／ 取得枠 |
| 希望提出期間 | 本 ／ 取得枠 ／ 希望 |
| マッチング実行待ち | 本 ／ 取得枠 ／ 提出した希望 |
| 結果公開 | 成立と返却の内訳（6.2 の見出しと揃える） |

参加人数を出すのは登録期間までとする。それより後は登録の締切が過ぎており、まだ登録していない人が何人残っているかを数える用が無い。代わりに自分の希望の冊数を出す。取得枠に対して足りているかどうかが、その時期にいちばん確かめたい数になる。準備中の取得枠は0ではなく「—」と書く。0冊と書くと受け取れないと読めるが、まだ登録が始まっていないだけにあたる。

#### URL

**交換会ページの URL は交換会そのもの（`/exchanges/:id`）とする。** 本の一覧のための別の URL は持たない。1つの画面に2つの入口ができると、交換会一覧のカードやパンくずがどちらを指すのかを画面ごとに選ぶことになる。

**`/exchanges/:id/books` からの転送も置かず、経路そのものを持たない**（`decisions/0012`）。同じ URL は本の登録を受ける POST のルートとしては使うので、持たないのは読む経路に限る。

絞り込み（6.2）はこの URL のクエリに載せる。

#### 誰が開けるか

開けるのは参加者だけとする。取得枠は参加を持たない人には存在せず、この画面の情報の半分が成り立たないため。開けない場合は 404 を返す（8. 情報の可視性ルール）。主催者は必ず参加者を兼ねるので（6.9）、自分の交換会を開ける。

**主催者管理画面への導線はこのページが持つ。** 状態ヘッダーの中に置き、主催者にだけ出す。押しても 404 になるリンクは見せない。管理画面へ入る経路はこの1本だけ（6.8 / `decisions/0012`）。

交換会を作った直後の着地もこの画面とする。作った時点で参加が成立しており、編集画面は設定を直しに戻る画面であって、作り終えた人を最初に置く場所ではない。

参加が成立したあとの着地もこの画面とする。招待URL着地画面は未参加の人のための画面で、参加を終えた人を留める場所ではない。ログインを挟む経路も挟まない経路も着地は同じにする。ただし参加できなかった場合だけは招待URL着地画面へ戻し、理由をそこで説明させる（6.7）。

### 6.2 交換会ページ — 本の一覧 ＋ 希望リスト編集

6.1 の状態ヘッダーの下、同じページの下半分にあたる。登録された本をすべて表示する。フェーズによって振る舞いが変わり、**読み取りは5フェーズすべてで開いている。**

**準備中**

- 並ぶ本がまだ無い。空だと分かる面を置き、いつ並び始めるのかを書く
- 空白のまま落とすと、読み込みに失敗したのか、まだ誰も登録していないのかが読み取れない
- **面そのものは登録期間で0冊のときと同じものを使い、差し替えるのは文だけとする。** 0冊という同じ状態が、フェーズによって別の形で出ると読み替える手間が増える。空だと分かれば足りるので、カードの入る場所を枠で象る必要はない
- 文は「登録期間が始まると、ここに並びます」とする。登録期間の「誰かが登録すると、ここに並びます」をそのまま使わないのは、準備中に空なのは、まだ誰も登録していないからではなく、登録できる人がまだ居ないため。誰かの登録を待っているように書かない
- 登録期間の開始日時はここに書かない。状態ヘッダーの「あなたがすること」が同じ日時を出している（6.1）

**登録期間中**

- 全員の本がカード形式で並ぶ
- 誰が登録したかが分かる
- 自分の本には編集・削除の導線がある
- 「本を登録する」ボタン

**希望提出期間中**

- 同じ一覧に「希望に追加」ボタンが付く
- 画面の右側（またはモバイルでは下部）に、現在の希望リストが常時表示される
- 希望リストはドラッグで並べ替えられる。順位が明示される
- 自分の本は選べない（グレーアウトなど）
- 冊数の目安を示す。「取得枠2冊に対して希望3冊。もう少し増やすことを推奨します」のような案内
- 何人がその本を希望しているかは **表示しない**

**マッチング実行待ち**

- 希望リストは並びを保ったまま残し、編集の操作だけを外す。見出しは「提出した希望リスト」に変える
- カードには、自分がそれを何位で出したかを添える
- 締め切られた事実だけを消して並びも消すと、自分が何を出したのかを確かめる先がどこにも無くなる。**出すのは自分の希望だけで、他人の希望も、その本を何人が希望したかも出さない**（8.）
- **置き場所も枠も希望提出期間と同じものを通す。** 広い画面では一覧の右、狭い画面では下部のシート。別の場所へ移すと、締切をまたいだ瞬間に希望リストが消えたように見える
- **カードの幅も希望提出期間と同じにする。** 右のリストが同じ幅を取り続けるため。参加者が実際に通るのは希望提出期間から実行待ちへの遷移で、そこでカードの大きさが変わると、読み比べていた並びを覚え直すことになる
- **希望に入れなかった本には何も書かない。** 順位が出ている本が同じ画面に並んでいるので、出ていないことがそのまま入れなかったことにあたる。入れなかった側にも一文を置くと、十数枚のうち大半が否定の文を持つことになり、読むもののほとんどが「入れていません」で埋まる。数そのものは状況の数字の「提出した希望」と、右のリストが持っている
- 自分の本も同じ扱いにする。希望に入れようがないので順位を持たず、下段そのものを出さない。書けない理由はカードの「自分の本」の印が示している。「行き先は結果公開で分かります」のような一文も置かない。状態ヘッダーの「主催者がマッチングを実行すると結果が公開されます」と同じことを1画面で2度言うことになる
- 順位は朱ではなく生成りで置く。朱は押すものと締切の担当なので（10.1）、動かせなくなった順位に残すと、まだ押せるものが混じっているように読める
- 冊数の案内（「取得枠2冊に対して希望3冊」）は持たない。増やす道がもう残っておらず、促しが果たせない。取得枠そのものはシートの下部に残す
- 締切の行の代わりに、上位が他の人に渡ったときは下の順位が繰り上がることを書く。締切はもう過ぎているので、次に来る日時としては出さない
- 1冊も出さなかった人には、割り当てられる本が無いことを書く。選び方を教えても間に合わない

**結果公開後**

- 成立した本には受け取った人の名前が表示される
- 返却された本にはその旨が表示される

本のカードに載る情報：タイトル、登録者名、あらすじの冒頭、おすすめポイント。ギフトコードは載せない。おすすめポイントは朱の縦線を引いてあらすじより前に置く。あらすじを先に置くと、どの本にも似た筋書きが並び、読み比べる材料が下に沈む。

**カードは縦1列に積む。** 気になった1枚はその場で開く。閉じている間はおすすめポイントを2行、あらすじを1行に折り、開くと下へ伸びて全文が出る。詳細画面へ飛ばさないのは、読み比べの途中でどこまで見たかを見失わせないため。

**横には並べない。** 1列なら開いても下が押し下がるだけで、横は動かない。詳細画面へ飛ばさないのと同じところに乗る理由で、横に並べると1枚開いたときに以降のカードの位置が動く（`decisions/0014`）。

**一覧の幅は、希望リストが脇に並ぶ間の幅（768px）で止める。** 止めないとリストの無いフェーズだけカードが1100pxを超え、1行が80字を回って読み比べられなくなる。フェーズをまたいでも幅が変わらないことのほうも要る。読み比べていた並びを覚え直さずに済む（実行待ちの項も同じ）。

**開いて変わるのは、折っていた本文が伸びることだけとする。** 見出し（「おすすめポイント」「あらすじ」）も、ストアへのリンクも、題の大きさも、閉じている間から同じ場所に同じ大きさで置く。開いた瞬間に見出しが生え、題が大きくなり、ボタンが別の場所へ移ると、読み比べていたカードを見つけ直すことになる。列の中でカードの位置を動かさない理由（上）と同じものが、1枚のカードの中でも要る。

見出しは折った本文にこそ要る。それが何の抜粋なのかを、開くまで名指せなくなるため。ストアへのリンクも同じで、買う先を見るのに本文を開かせる理由が無い。

**開くボタンと閉じるボタンは同じ1つにする。** 文字だけを「続きを読む ↓」「閉じる ↑」で差し替える。別々のボタンを置くと、押した指の先でボタンが入れ替わる。2つの文字は重ねて置き、長いほうの幅で場所を決める。短いほうへ変わったときに、隣に並ぶ操作が寄ってこない。

**折って隠れている本文が無いカードには、開くボタンを出さない。** 押しても何も起きないボタンになる。**何行に折れるかはサーバー側では決められない。** 同じ本文でも画面の幅と字形で変わるため、伏せた状態で描いておき、ブラウザで測ってから出す。幅が変われば折れ方も変わるので測り直す。字形が決まる前に測ると、代替の字で収まっていた本文が本来の字で溢れる。

このため開くボタンは JavaScript が動く環境にしか出ない。押しても開かないボタンを残さないためで、並べ替えのハンドルと同じ扱いにあたる。ただし本文が折られたままになることは引き受ける（`decisions/0014`）。

**ストアへのリンクは本文より上、カードの右上に置く。** 下段に置くと、開くボタンが出ないカードでは1つぶん左へ寄り、同じリンクがカードごとに別の場所に出る。上に置けば、下段に何が並ぶかと無関係に位置が決まる。

**形は文字のリンクではなくボタンにする。** この画面から出ていく唯一の導線で、下段に並ぶ文字のリンクに混ぜると読み流される。ただし朱は使わず生成りの輪郭で置く。一覧で朱を担うのは希望の出し入れで（10.1）、十数枚ぶん並ぶ朱の中にもう1つ足すと、押してほしいものの順が読めなくなる。

題と同じ行に並べ、入りきらないときは題を削らず、印とボタンのほうを次の行へ落とす。日本語の題はどこでも折り返せるので、詰めると1行に数文字しか残らない。

**下段は、この本に対してできることだけを集める。** 中身が全部伏せられたときは段ごと消す。罫線だけが引かれた面が十数枚ぶん並ぶことになるため。本文の脇に段は作らない。脇は幅を譲らないので、375pxで横に並べると本文が数十pxまで削られ、1行に1文字ずつ落ちる。

開閉は Stimulus で持つ。本文はギフトコードを含まないので全文を最初からカードに入れ、抜粋は CSS で折る。Turbo Frame にすると1枚開くたびにサーバーへの往復が挟まる。

**いまはページングも「もっと見る」も持たない。** 判断が乗っている前提は、1つの交換会は数人から十数人という見積もり（10.）。1人が数冊出しても数十枚に届かない。規模と無関係な理由もあり、区切ると読み比べの途中でどこまで見たかを見失わせることになって、カードをその場で開く判断（上）と噛み合わない。

**見出しはカードの並びの説明だけを持つ。** 「みんなの本」と冊数、絞り込み、結果公開後は「誰に渡ったか」の断り書き。フェーズごとの「次にすること」も、参加人数も取得枠も、状態ヘッダーが上で出しているので繰り返さない（6.1）。同じページに2つ載せると、同じ数字が縦に2度並ぶ。ここに残す冊数は、いま並んでいるものが何枚なのかを一覧の直前で言うためのもので、状況の数字とは役目が違う。

結果公開後は、カードの下段に「登録者 → 受け取った人」を1行で出す。自分が関わる側は名前ではなく「あなた」にする。十数枚並ぶ中から自分の名前を探し直さずに済ませるためで、結果画面の全体一覧と同じ扱いにする。自分が受け取った本だけは輪郭を松葉にして「あなたへ」の印を付け、返却された本はカードごと面を沈める。松葉が付くのは渡った先だけで、返却に朱や取り消し線は使わない。**返却の理由はここには書かない。** 誰にも希望されなかったことを一覧の十数枚に並べると、渡らなかった事実より理由のほうが目に残る。理由と、コードが手元に残っていることは 6.5 が引き受ける。

**渡った先を出すかどうかはフェーズで決める。** 割当の有無で決めると、主催者がマッチングを実行した瞬間に、公開の合図をまだ受けていない画面へ結果が出る。割当を持たない本は返却として扱う。結果公開後にそうなる本は無いが、全体の一覧（6.5）と読み方を揃えておく。

結果画面への口は状態ヘッダーが持つ（6.1）。結果公開後の状態ヘッダーは松葉の面に変わり、受け取った冊数と贈り主を出したうえで、そのまま結果への入口になる。ギフトコードの取り出し口は結果画面だけなので（6.3）、カードで渡った先を見た人は上へ戻れば入れる。畳んだ帯にも残るので、下まで読んでから探し直すことにはならない。

一覧は「すべて」と「自分の本」で絞れる。絞り込みは URL のクエリに残し、開き直しても同じ並びで戻れるようにする。状態ヘッダーの数字は絞っても交換会全体のまま出す。ここで一緒に動かすと、登録がどこまで進んだのかが読めなくなる。

ストアへのリンクは http と https だけを開く。登録者が書いた URL をそのままリンクにするため、`javascript:` を書いて登録されると、読み比べに来た参加者のブラウザでそのまま走る。

希望リストの順位は1から始まる連番で保つ。1冊外したら残りを詰め直す。穴が空いたままだと、次に足した1冊の順位が飛び、画面に出す順位とリストの何番目かが食い違う。順位の重複はデータベースの制約でも塞ぐ。重複すると順位順に読んだ並びが不定になり、乱数シードを固定してもマッチングの結果を再現できなくなる。

追加と削除は1冊ずつその場で保存し、並べ替えは順序だけを保存する。並べ替えの保存は、送られてきた本の集合が現在の希望リストと一致することを求め、一致しなければ拒否して画面を読み直させる。集合が食い違うのは別のタブで追加や削除をしたときで、届いた並びを正として差分を反映すると、そちらの変更が気付かれないまま消えるため。

同じ本を二度追加しても、二度目は何も起きず同じ希望を返す。希望していない本を外そうとしたときも同じ。どちらも二度押しや再送信で落とすようなことではない。

冊数の案内は、取得枠と現在の希望冊数を並べたうえで、希望が取得枠の2倍に満たないときだけ増やすことを促す。2倍ちょうどは満たしているものとして扱う。ここを短いほうへ寄せると、推奨どおりに並べ終えた人にまで増やせと出続ける。取得枠が0の人には促さない。希望提出期間に入った時点で登録期間は終わっており、増やす道が残っていないため、受け取れる本が無いことだけを伝える。面を朱で塗るのも促すときに限る。数えるのは自分の取得枠と自分の希望だけで、その本を何人が希望しているかは案内にも現れない。

案内は畳んだシートにも1行で出す。狭い画面では畳んだ状態が既定なので、開いた側にしか置かないと、一覧を読み進めている間ずっと冊数がどこにも出ない。取得枠そのものは締切と同じくシートの下部に置く。希望提出期間には本を足せず取得枠が動かないので、差し替えの外にあっても古くならない。

希望リストは広い画面では一覧の右に並べ、狭い画面では下部に固定したシートにする。シートは畳んだ状態でも順位付きのチップが横に並び、一覧を読んでいる間ずっと何冊・何位まで選んだかが見えている。

**足すボタンはカードの側だけに置き、外すボタンは両方に置く。** 押す対象は本のカードで、リストは今の並びを映すもの、という役割の分け方は、外すときだけ成り立たない。リストを見て「これを消したい」と思った人に、同じ本のカードを十数枚の中から探し直させることになるためで、そのとき押したい対象は、映している側そのものにあたる。足すボタンをリストに置かないほうは変わらない。リストに無い本をリストから足すことはできない。

**外すボタンを置くのは、開いた側の行だけとする。** 畳んだ側のチップは横に流れる要約で、44pxのボタンを並べると1画面に2冊ぶんしか入らない。一覧を読んでいる間ずっと何冊・何位まで選んだかが見えている、というのが畳んだ側の役目なので、そちらを削ってまでボタンを置かない。

行の外すボタンは、並べ替えと違って JavaScript が無くても押せる。カードの側と同じ送り先を同じ形で叩くだけで、押せば後ろの順位も繰り上がる。**このため、並べ替えの form は行を包まない。** form は入れ子にできず、内側はブラウザに落とされる。順序を送る hidden は行の中に置いたまま form 属性で結ぶ。送られる順は form の中の並びではなく DOM の並び順なので、外へ出しても送る並びは変わらない。

1冊出し入れするたびに差し替えるのは、カードの一覧と希望リストの中身の2か所。1冊外すと後ろの順位がすべて繰り上がるので、押したカード1枚だけでは繰り上がった他のカードの順位が古いまま残る。開閉の状態を持つシートの外枠は差し替えの外に置く。ここを含めると、シートを開いて操作した瞬間にシートが閉じる。JavaScript が無い場合は一覧へ戻す。絞り込みは URL に残っているので、どちらの経路でも持ち回す。

**並べ替えの操作はハンドル1つにする。** ポインタではつまんで動かし、キーボードではハンドルへフォーカスして ↑↓ で1つずつ動かす。動かした行は落とす前からその場に差し込み、順位もその場で振り直す。行そのものが動くので、落ちる位置を別に描かなくても、いまどこへ入るかが順位ごと見えている。

**↑↓ のボタンは置かない。** キーボードと読み上げに渡る道は、ハンドル自身が持つ（下）。行に並べるボタンの数がそのまま題に渡る幅を決めるので、同じ道に2つのボタンを置かない（`decisions/0013`）。

**そのハンドルは行の順位そのものにする。** 押すものを行の両端に離すため。44pxの的が数pxの隙間で並ぶと、並べ替えようとして希望から外す取り違えが起こりうる。外すほうは確認を挟まずその場で消えるので、間違えたときの損が大きい（`decisions/0013`）。

**順位は輪郭で押せることを言う。** 数字は、その形だけでは押せることを言わない。朱はすでに順位に乗っているので（10.1）、合図を色で足す道も塞がっている。止まっている間から外すボタンと同じ輪郭を持たせて、押せるものであることを見せる。輪郭を共有しても、行の反対の端にあるので取り違えない。

**ハンドルは外すボタンと同じ44px（広い画面は32px）にする。** 指で押す並べ替えの操作がここだけなので、押せる大きさのほうを採る。素の文字で置くより題は削れるが、押せるかどうかと引き換えにする幅ではない。

**このためハンドルを読み上げに渡す。** ボタンにして名前と操作の説明を持たせる。名前は見えている数字に題を続けて組み、「1位「◯◯」を動かす」と読ませる。aria-label で上書きしないのは、動かすたびに振り直す先が数字と名前の2か所になり、片方だけが古くなるため。動かした結果は、変わった順位を読み上げる区画で伝える。行を DOM から抜き差しするとフォーカスが外れるので、動かしたあとはハンドルへ戻す。

**順位は伏せられない。** 並べ替えのハンドルは JavaScript が動いてから出すが（下）、順位はボタンである前に読むものにあたる。連結するまでは押せない状態で出し、輪郭とカーソルのほうを外す。マッチング実行待ちの順位はボタンにしない。押せない順位と押せる順位が同じ数字で並ぶので、締め切られた側は輪郭も朱も持たせず、生成りの素の文字に落とす。

**「1つずつしか動かせない」への答えは Home / End が持つ。** ポインタで触れる人はドラッグで一息に動かせるが、キーボードだけの人には同じ道が無い。端へ送るキーなら、ボタンを1つも増やさずに渡せる。

**つまむのが難しい人には、押せば動くボタンが残らない**（`decisions/0013`）。キーボードには残るが、目で見つかる道ではない。リストの上に操作を1行で書き、ハンドルからも同じ説明へ繋ぐ。

つまんでいる行は、面を淡い朱で塗り、輪郭を朱の破線にし、ハンドルの輪郭も朱にする。ハンドルの字はもとから朱なので、ここで変えられるのは輪郭のほうにあたる。輪郭の線種だけを変えても、ハンドルを捉えられたのかどうかが読み取れない。**合図は色で持つ。** 指には cursor が無いので、`cursor: grabbing` だけでは狭い画面に何も残らない。ここで朱を使うのは、つまんでいる行がまさに押されているものにあたるため（10.1）。落とせば描き分けごと外し、元の見た目へ戻す。**変えるのは色と輪郭の線種と位置だけで、行の中身と大きさは動かさない。** つまんだ瞬間に外すボタンが消えたり影が付いたりすると、掴み直すたびに行の形が変わる。

**つまんでいる行はポインタに追従させる。** 差し込みで動くのは行の居場所で、見た目のほうは指の下に置いていく。居場所が1つぶん飛んだぶんは打ち消す。打ち消さないと、順位が入れ替わるたびに行が指から離れて跳ねる。スロット単位で飛ぶだけだと、指と行のあいだが常にずれていて、持ち上がっている感触にならない。影が使えない以上（10.1）、掴んだ手応えは追従そのもので出すほかない。持ち上げた行は隣と重なるので、重ね順を上げる。

ハンドルには `touch-action: none` を置く。置かないと、指で下ろした瞬間に並べ替えではなく画面がスクロールする。ポインタの捕捉（`setPointerCapture`）は使わず、続きは window で受ける。捕捉した要素を DOM から抜き差しすると、その時点で捕捉が解ける。差し込みのたびに行を抜き差しするため、1行ぶん動かしたところで追従が止まる。

並べ替えのハンドルは JavaScript が動いてから出す。追加と削除には JavaScript の無い経路があるが、並べ替えには無い。出したままにすると、押しても何も起きないボタンが残る。ハンドルが順位そのものなので、伏せるのではなく押せなくする（上）。続けて押されたぶんは少し待ってからまとめて送る。1回ごとに往復すると、順位を何段も上げている最中に画面が入れ替わる。

### 6.3 本の詳細（持たない）

1冊だけを開く画面は作らない。載せるものがすべて他の画面にあり、この画面にしか無い情報が残らなかったため。

タイトル、登録者名、おすすめポイント、あらすじ、ストアへのリンクは 6.2 のカードが持つ。カードは全文を最初から含んでいて、開けばその場で読める（6.2）。ギフトコードは 6.5 の結果画面が持つ。

ギフトコードを読む画面は、登録期間中の編集フォーム（6.4）と結果公開後の結果画面（6.5）の2つとする。コードを読みたくなる場面は登録期間中（入力の確かめ）か、結果公開後（受け取った本を使う、返却された自分の本を使う、相手から使えないと言われて確かめる）のどちらかで、その間の希望提出期間とマッチング実行待ちには、コードを読んでできることが無い。8. の「登録した本人（常時）」は**誰に見せてよいか**の規則であって、どのフェーズにも表示画面を置けという要求ではない（`decisions/0015`）。

このため 6.5 は、受け取った本のコードに加えて、**返却された自分の本のコードも開けるようにする。** 誰にも渡らなかった本のコードが、どこからも取り出せなくなるのを防ぐ。

一覧にコードを載せて代わりにすることはしない。カードが十数枚並ぶ画面で開かせると、肩越しに1枚も覗かれずに済ませるのが難しい。可視性の判定を一覧側に持つこと自体も避ける（8.）。

### 6.5 結果画面

結果公開後に開く、この交換会のクライマックスとなる画面。

**上部：自分が受け取った本**

- タイトル、登録者名、おすすめポイント
- ギフトコード（伏せ字＋表示ボタン、コピーボタン）
- 誰から贈られたかが分かる（お礼を伝えるため）
- 自分の本が返却された場合は、その旨をやわらかく伝え、**その本のギフトコードも同じ形で開けるようにする**。詳細画面を持たないので（6.3）、誰にも渡らなかったコードを取り出せる場所がここ以外に無い

**中部：自分が出した本の行き先**

- 自分が登録した本と、それを受け取った人の名前。返却された本はその旨
- 全体の一覧にも同じ本が並ぶが、十数行の表から自分のぶんを探させないために抜き出す

**下部：全体の成立結果**

- 誰が誰の本を受け取ったかの一覧
- 成立した冊数と返却された冊数
- ギフトコードは当然表示しない
- ドラフトの抽選順（8.）。畳んでおく。巡ごとに順序が逆になることを添える。並びだけを出すと、早く引いた人が得をしたように読める
- 本が1冊も登録されないまま実行された交換会（9.）では、この節ごと畳む。見出しと列名だけの表は何も伝えない

**何番目の希望で渡ったかは、どこにも出さない。** 受け取った人の希望リストの中身にあたり（8.）、1冊でも順位を出せばその人のリストの一部が漏れる。加えて、順位が低いと渡った事実より順位のほうが目に残る。返却について「選ばれなかったことを本の評価として読ませない」と書いているのと裏腹になる。

**抽選順はマッチングの実行時に保存する。** 読むときに乱数シードから引き直すこともできるが、乱数の消費順という `Matching::Engine` の内部に画面が依存し、エンジンを変えた瞬間に保存済みの割当と表示がずれる。実行前は空で、抽選順を持たない交換会では畳んだ節ごと出さない。

受け取った本は、マッチングで確定した巡の順に並べる。余り物の割当は巡を持たないので最後に置く。希望の上位から取れた順という読み方を保つため。

**結果公開前にこの画面を開いたときは 404 を返し、本文は描く。** 導線は公開後にしか出ないので、ここへ来るのは URL を直に打った場合だけになるが、素の 404 だと URL を間違えたのか時期が早いのかを参加者が区別できない。実在を伏せる必要があるのは主催者だけが開ける画面で（8.）、ここへ来られるのは交換会も現在のフェーズも既に見えている参加者にあたる。参加していない人には交換会そのものが見つからず、素の 404 になる。

**受け取った本が0冊のときは、取得枠が0だった場合と、枠はあったのに回ってこなかった場合を言い分ける。** 前者は登録期間に1冊も登録しなかった結果で（3.）、後者は参加者と冊数の巡り合わせで起きる。同じ文で片付けると、登録したはずの人が登録し忘れを疑うことになる。どちらも締め出されたのではなく仕組みの結果なので、そのことを書く。

ギフトコードのコピーは、伏せ字のまま押せるようにする。開かずに済むなら、そのほうが肩越しに覗かれる機会が少ない。

### 6.6 交換会一覧

自分が参加している交換会をカードで並べる。各カードに交換会名、現在のフェーズ、主催者名、参加人数、「すべきこと」の1行、次の締切。

「すべきこと」の1行は交換会ページの「あなたがすること」と同じもので、置き場所も同じサービス（`Exchanges::Todo`）から引く（6.1）。2か所で別々に組むと、片方だけが古い言い方で残る。カードに出すのは見出しのほうだけとし、補足は開いた先に任せる。数週間ぶりに開いた人がこの画面で決めるのは「どれを開くか」までで、そこから先は交換会ページが引き受ける。

主催者が自分のときは名前ではなく「あなた」と書く。自分の名前を出しても、誰のことか読み替える手間が増えるだけ。

見出しの下に置くのは並び順の説明だけとする。並びが日時の1本の軸であることは、カードを見ても分からない（下）。1つも参加していないときは、並ぶものが無いのでこの一文も置かない。

**いま動いている件数は出さない。** 動いているとは、書き込みが開いている（登録期間か希望提出期間にある）ことで、これはカードの強さの3段階で朱になるものと同じ範囲にあたる（下）。**朱のカードの枚数と、動いている件数は一致する。** 判断が乗っている前提は、参加数が多くても十数件という見積もり（10.）。目で数えられる枚数しか並ばない画面で、同じものを文字でも数えることになる。件数を出さないので、0件のときの言い分けも持たない。

ログイン済みでトップページを開いたときの着地はこの画面とする。未ログインならログイン画面へ送り、認証を終えたらここへ戻す。**未認証の着地に説明のための画面は挟まない**（5.）。1つも参加していないときにこの画面が出す主催の目安と交換会をつくるボタン（下）が、そこで説明することにあたるものを、認証の後で引き受けている。

参加した交換会だけが並ぶ。主催者は必ず参加者を兼ねるので（6.9）、自分が主催した交換会もここに並ぶ。主催者管理画面への導線は交換会ページが持つ。

「次の締切」はフェーズによって指すものが変わる。準備中は登録期間の開始、登録期間は登録の締切、希望提出期間は希望提出の締切。マッチング実行待ちと結果公開には日時が無い。前者が待っているのは主催者の操作で日時では動かず、後者はもう終わっているため。準備中に「締切」と書かないのは、まだ始まってもいない登録がもう終わるように読めるため。

日時が無いフェーズでも、締切の欄そのものは消さない。空けてしまうと、締切を見落としたのか、そもそも無いのかが読み取れない。マッチング実行待ちは「なし」と書き、することが無いことを添える。結果公開は締切の代わりに、公開した日時と結果画面への導線を置く。この画面から結果へ入れるのはここだけで、それ以外の経路は交換会ページが持つ（6.1）。

日時のあるものには、残りの長さを主に出し、日時そのものは補足へ下げる。日付だけでは、それが今日中なのか来週なのかを毎回読み解くことになる。数え方は 6.1 と同じ（いちばん大きい単位ひとつ、端数は切り捨て、1分を割ったら「まもなく」）。

カードの強さは3段階にする。締切まで24時間を切ったものだけを朱の面にし、それ以外の締切があるものは朱の文字、準備中は生成りへ沈める。何枚並んでも朱の面は迫ったものだけなので、ざっと見て1枚だけが目に飛び込む。準備中を残り時間で急かさないのは、待っているのが締切ではなく開始で、急いでも早められないため。結果公開は松葉の枠にする（10.1 の色の担当のとおり）。

並び順は次の締切が近い順とし、締切を持たないマッチング実行待ちと結果公開を下へ送る。締切を持たないものどうしは日程（登録期間の開始）の新しい順。準備中の「登録期間の開始」も同じ軸に混ぜる。まだ何もできない交換会が上に来ることはあるが、フェーズで群に分けると、フェーズが変わった瞬間にカードが群をまたいで大きく動く。日時は1本の軸なので、時が進んでも位置が少しずつしか動かない。参加数は多くても十数件を想定しており、開くたびにカードの位置が入れ替わらないことを優先する。

**いまは一覧に絞り込みを置かない。** フェーズでも、自分が主催しているかどうかでも絞れない。この画面が答えるのは「どれを開くか」までで、探す画面ではない。**判断が乗っている前提は、参加数が多くても十数件という見積もり**（10.）。全件を締切の近い順に並べて困る数にならないという読みで、終了したものを畳むボタンを置いていないのと同じところに乗る（`decisions/0010`）。規模と無関係な理由も2つあり、そちらは `decisions/0016` にある。

増え続けるのは結果公開のぶんだけで、締切を持たないので並びの末尾に沈む。件数が増えただけでは前提は崩れない。`decisions/0016` の2つは規模とは無関係なので、前提が崩れても残る。

1つも参加していない場合は、その旨と、招待URLから参加できることを示す。あわせて主催するときの目安（人数と各期間の長さ）と、交換会をつくるボタンを置く。この画面から動く道は「招待URLを待つ」か「自分でつくる」の2つしかなく、後者を選ぶ人は、何人でどれくらいの期間かの見当が付かないと日時を決められない。

交換会を新しくつくるボタンは、この画面の本文が持つ。主催をはじめる道はここにしかない。並ぶものが有るときは見出しの右に置く。カードの並びの中に置くと交換会でないものが1枚だけ紛れるが、並びの外にある見出しの右なら混ざらない。共通ヘッダーには置かない。同じ行き先が1画面に2か所あると、どちらが正しいのかを押す前に考えることになる。結果画面への導線を1か所に絞っているのと同じ理由。

ボタンの見た目は、並ぶものが有るときは輪郭にし、1つも参加していないときだけ塗りにする。朱で塗ると、締切まで24時間を切ったカードの朱の面と競る。ざっと見て朱の面が1枚だけ目に飛び込むのが前段の作りなので、その相手が並んでいる画面では輪郭へ落とす。カードが1枚も無い画面には競る相手がいないので、押してよいものだと分かる大きさに戻す。

### 6.7 招待URL着地画面

未参加の人が招待URLを開いたときの画面。交換会名と概要、主催者名、参加者数、各期間の日程を見せて「参加する」ボタン。未ログインならログインへ誘導し、戻ってきたら自動で参加処理を行う。

登録期間が終わっている場合は参加できない旨を表示する。

招待された人については、参加が成立するのはボタンを押した人だけとする。招待URLを開いただけで立ち去った人を、後のログインで参加させてはいけない。未ログインのボタンは「ログインして参加する」とし、押した事実をサーバー側に保存してからログインへ送る。画面を開いた時点では保存しない。

主催者はこの経路を通らない。交換会を作る操作が、そのまま参加の意思表示にあたる（6.9）。主催者がこの画面を開いた場合は参加済みとして扱い、辞退のボタンは出さない。

ログインの往復中に登録の締切をまたぐことがある。この場合は参加を見送り、ログインだけ成立させる。参加できなかった理由は、戻った着地画面が現在のフェーズから説明する。

日程は「本を登録する ／ 欲しい本を希望順に並べる ／ 結果公開・ギフトコードを受け取る」の3段で見せる。段ごとに開始日時と、そこで効く決まり（登録した冊数と同じだけ受け取れる、自分が登録した本は選べない）を添える。日時だけを並べても、数週間拘束されることを承知で参加するかどうかは決められないため。

段の開始日時は「◯◯から」と書き、範囲では書かない。各段の開始が前の段の締切にあたるので、範囲で書くと同じ日時が2度出る。結果公開だけは「◯◯以降」とする。公開は主催者がマッチングを実行したときに起きるもので、日時では決まらない。希望提出の締切はその下限にあたる。

段はフェーズと1対1ではない。マッチング実行待ちに当たる段は無く、希望提出が終わって結果公開を待っている状態にあたる。参加できないときは各段に終了・進行中・予定を添えるが、マッチング実行待ちでは3段目を進行中にしない。まだ結果は見られないため。

参加できない場合も、概要と日程は見せたままにする。あわせて理由（途中から加わると登録冊数と取得枠の釣り合いが崩れる）を書く。理由が無いと、主催者に掛け合えば入れてもらえるようにも読める。

参加できない場合の交換会一覧への導線は、ログイン済みのときだけ出す。未ログインの人は参加していないので一覧が空になり、参加できないと言った直後にログインだけを促すことになる。

### 6.8 主催者管理画面

- 参加者一覧（名前、登録冊数、希望提出済みかどうか）
- 参加者の除外（登録期間の締切まで）
- 招待URLの表示・コピー・再発行
- 各期間の日時変更
- 通知用 Webhook URL の設定
- **マッチング実行ボタン**

この画面へ辿り着く経路は交換会ページだけとする（6.1）。交換会一覧は主催と参加を区別せずに並べるので（6.6）、そこに導線を置くと、カードごとに主催かどうかを見分けさせることになる。導線は主催者にだけ出す。押しても 404 になるリンクは見せない。

**フェーズによる制限は掛けず、どのフェーズでも開ける。** 締切を延ばすのも（6.9）マッチングを実行するのもこの画面の仕事で、特定のフェーズで閉じると主催者が自分の交換会に入れなくなる。

招待URLはホストごと表示し、コピーできるようにする。渡された側がホストを補うことなく、そのまま貼って開ける形にするため。締切を過ぎるとこのURLからは参加できないので（6.7）、その旨も添える。

**招待URLの再発行にもフェーズによる制限は掛けない。** 配り直したい理由は「渡してはいけない相手に渡った」ことが多く、締切の前後で急ぎ具合が変わらない。締切後に配り直しても、参加を断るのは着地画面の仕事で変わらない。再発行で開けなくなるのは古いURLだけで、既存の参加は影響を受けない。参加は利用者と交換会で結ばれていて、招待トークンを見ないため。

取り消せない操作なので、再発行の前には確認を挟む。

**日時の入力欄はこの画面には置かず、交換会の編集画面（6.9）に1つだけ置く。** この画面には現在の日程を期間ごとに並べ、「変更」から編集画面へ送る。日時は3つで互いに順序の制約を持つため、入力欄を2箇所に増やすと、片方だけで検証の順序や既定値が食い違う。並べるのは登録期間と希望提出期間の2つで、結果公開は含めない。公開は主催者の実行で起きて日時では決まらないため、動かせる期間ではない。

各期間には終わった・進行中・これからの別を添える。日時を読み比べて今どこにいるかを主催者に数えさせないため。

締切を動かすとフェーズはその場で切り替わり、参加者の画面の残り時間も即座に変わる。フェーズが状態カラムではなく日時から導出されるためで（4.）、その旨を日程に添える。

**結果公開後も日程は変更できる**（6.9）。ただし変更しても結果公開のままなので、締切を戻せば登録や希望提出が開き直ると読ませてはいけない。フェーズはマッチングを実行したかどうかで決まり（4.）、結果公開はどの書き込みも許さないため、日時をどこへ動かしても開くものは無い。ギフトコードの可視性も同じ判定に乗っているので変わらない（8.）。結果公開のときは「日程を変更しても結果公開のままで、本の登録や希望の提出は再開しません」と、再開しないものを名指しして添える。「表示だけが変わる」と書くと、何が変わらないのかが伝わらない。

参加者一覧には名前、登録冊数、希望提出の有無と提出した冊数、参加日を出す。**何を希望したかは出さない**（8.）。順位まで見える立場ができると、割当の前に結果を組み替えられる。提出した冊数だけなら、誰がどの本を欲しているかは分からない。

登録冊数が0の参加者は取得枠が0で、本を受け取らない（6.9）。締め出されたのではなく仕組みの結果なので、そのことを一覧に添える。書かないと、主催者が登録を誤って消したのかと疑う。

参加者の除外は一覧の行に置く。誰を外すのかは名前と登録冊数を見て決めるので、別の画面へ送ると判断材料を置いてくることになる。**除外できないフェーズでは列ごと畳む。** 主催者の行にもボタンは出ない（4.）。押しても断られるボタンは残さないが、ボタンが消えたことを不具合と読まれないよう、いつまで外せるのかは一覧の下に添える。外すと登録した本もギフトコードも消えるので、確認を挟む。冊数は同じ行に出ているので、確認の文では繰り返さない。

除外の経路は辞退（6.7）と分ける。通す検証は同じでも、押せるのは主催者だけで、対象を選ぶぶん相手の指定が要る。1つの経路に混ぜると、自分を消すのか他人を消すのかを本文の値で見分けることになる。

マッチング実行は取り返しがつかない操作なので、確認を挟む。希望提出期間の締切後は、この画面に大きく「マッチングを実行してください」と表示する。押し忘れが起きやすいため。

**ただし実行を始められるのはこの画面だけではない。** 実行の確認画面へは、この画面と交換会ページの両方から入れる（6.1）。押し忘れが起きやすいのに、実行の導線が管理画面の中にしかないと、そこへ辿り着くまでが導線の細さで決まってしまう。実行待ちの主催者にとってその日すべきことは実行そのものなので、状態ヘッダーの「あなたがすること」からも始められるようにする。どちらの経路も可否は `Exchange#matching_executable?` で決まるので、片方だけが開くことはない。

**確認はブラウザのダイアログではなく、専用の画面で挟む。** 実行すると何人に何冊が渡り、何が思いどおりにならないのか（希望を出していない人数、1冊も登録していない人数、受け取り手のない本の冊数）を、押す前に数で示すため。ダイアログには要約を並べられない。同じ画面に、締切を延ばして待つ道も置く。招待URLの再発行や参加者の除外がダイアログで済むのは、失うものがその1つに閉じていて、数えて見せるものが無いため。

**確認画面もフェーズで閉じる。** 締切前と実行済みでは開かない。判定は実行そのものと同じ表から引く（4.）。開けたのに最後で断られるのでは、押せると思わせたまま断ることになる。

実行済みのときは、この画面から実行の導線を消し、実行日時だけを残す。マッチングは一度だけ実行でき、再実行できないため（3.）。日時を残すのは、いつ公開されたのかを主催者が参加者に答えられるようにするため。

参加者の登録冊数に極端な偏りがある場合（例：Aさんが5冊、他が1冊ずつ）、受け取れない本が出る旨の警告を出す。警告は登録期間の締切前に出す。締切を過ぎてからでは、主催者にできることがないため。

**判定は、最も多く登録した1人とほかの全員の合計を比べる。** 自分が登録した本は受け取れないので（3.）、1人の登録冊数がほかの全員の合計を超えると、超えた分は誰にも渡す先がなく登録者へ返る。返る冊数は「最多の人の登録冊数 − ほかの全員の合計」で、これが1冊以上のときに警告を出す。条件を満たす人は多くても1人しかいない。2人が同時に満たすとすると、その2人の冊数の和が総冊数を超えることになる。上の例は3人（5冊・1冊・1冊）なら3冊、6人（5冊・1冊×5）なら0冊で、人数まで決めないと冊数は出ない。

**この数は下限にあたる。** スネークドラフトは希望リストの上位から取っていくため、返却を避けられた組み合わせを取り逃すことがあり、実際の返却はこれより増えうる。冊数だけで決まる分は希望提出が始まる前から分かるので、登録期間中に出せるのはこちらだけになる。警告にも、これより増えることがある旨を添える。

警告を出すかどうかは、本の登録が書き込みとして開いているかで決める（4.）。日時を直に比べない。締切を過ぎれば追加登録を促す先が無く、結果公開後は日程を戻しても登録が再開しないため（6.9）、どちらでも出す意味がない。

### 6.9 交換会の作成・編集

交換会名、概要（自由記述。対応ストアや価格帯の目安をここに書く）、Webhook URL。

日時の入力は3つ。登録期間の終了と希望提出期間の開始は同時刻なので、1つの入力欄で兼ねる。

1. 登録期間の開始
2. 登録の締切（＝希望提出期間の開始）
3. 希望提出の締切

つくった人が主催者になる。主催者は params から受け取らない。編集できるのは主催者のみ。

**つくった人は同時に参加者にもなる。** 交換会の作成と主催者の参加は1つのトランザクションで作り、片方だけが残らないようにする。選ばせない。

参加していない人には交換会が見えない設計になっているため。交換会ページも結果画面も、参加していることを入場券にしている。主催者だけが参加者でないまま存在すると、どの画面も「主催者が来たらどうするか」を個別に答えることになり、主催者管理画面へ辿り着く経路も別に用意しなければならない。

運営に専念したい主催者は、本を1冊も登録しなければよい。取得枠が0になり、何も受け取らず何も出さない。これは 9. の「1冊も登録していない」状態そのもので、新しく扱う状態は増えない。

この結果、**作成時に限り、登録の締切が未来であることを求める。** 締切を過ぎた日程では参加を作れず、主催者が参加者になれないため。作成したあとは日時を自由に動かしてよい。参加はもう成立している。

日時のこれ以外の変更にフェーズによる制限は掛けない。主催者は各期間の日時を後から変更でき、結果公開後も変更できる（4. フェーズ）。

### 6.10 エラー画面

行き止まりでも次の一手を必ず置く。どの画面も「何が起きたか → 次に押すもの」の順に書き、原因の推測を並べない。数字コード（404 など）は見出しにせず、控えとして小さく置く。「予期しないエラー」「不正なリクエスト」とは書かない。

**4xx はアプリのレイアウトを通し、5xx は静的 HTML で返す。** `config.exceptions_app` を立て、400 / 404 / 422 だけをルーティングへ流して `ErrorsController` が描く。それ以外は Rails 既定の `ActionDispatch::PublicExceptions` に落ちる。500 が出ている状況では DB もセッションも読めないことがあり、アプリのビューを通すとエラー画面そのものを描けなくなるため。共通ヘッダーもログアウトも DB を要る。

描く側へ移した `public/400.html` `404.html` `422.html` は消してある。残すと `ActionDispatch::Static` が `/404` を先に拾って 200 で返し、手元で見た目を確かめる経路まで塞ぐ。development と test は `consider_all_requests_local` が真で例外の詳細ページが先に出るため、この直打ちの経路が唯一の確認手段になる。

`public/500.html` と `public/406-unsupported-browser.html` は Tailwind のビルド結果を参照できないので、配色を生の色コードで持つ。ロケールも引けないので、サービス名と題（「画面の名前 — おくりぼん」）も直に持つ。どちらも `@theme` と `ja.yml` に食い違わないことを spec で押さえる。406 は `allow_browser` がファイルを直に描くので `exceptions_app` を通らない。着く人のブラウザはこの道具が前提にしている CSS を読めないため、flex も grid も使わない。

**エラー画面は対象を引き当てない。** 交換会も利用者も引かず、引けたかどうかを本文に出さない。404 の文言は、参加していない交換会と存在しない交換会で完全に同じにする。ステータスを揃えても、文面が片方にしか当てはまらなければ、URL を試すだけで実在を確かめられる（8.）。

結果公開前の結果画面だけは例外で、404 を返しながら本文を描く。理由は 6.5。

**フェーズや役割が許さない書き込みの画面は、409 と 403 で組み立てを分けない。** 理由が違うだけで、断られた人がすることは「いまどうなっているかを読んで交換会へ戻る」で共通のため。現在のフェーズとできなかった操作は例外のメッセージが言い切る（11.）。画面はそれに、どの交換会での話かと、交換会ページへ戻るリンクを添える。書き込みの操作は交換会をまたいで同じ形をしているので、名前が無いとどれを操作していたのかが読めない。

**戻り先は例外から受け取る。** コントローラのインスタンス変数から拾うと、変数を置き忘れたアクションだけが戻り先を出せなくなる。

## 7. データ項目

| リソース | 項目 |
|---|---|
| 交換会 | 名前、概要、主催者、登録期間（開始・終了）、希望提出期間の終了、マッチング実行日時、招待トークン、乱数シード、Webhook URL |
| 参加者 | 表示名、アバター画像、参加日時、抽選順 |
| 本 | タイトル、あらすじ、URL、おすすめポイント、ギフトコード、登録者 |
| 希望 | 参加者、本、順位 |
| 割当 | 本、受取人、確定した巡、返却フラグ |

## 8. 情報の可視性ルール

デザイン上、絶対に守る必要がある。

| 情報 | 見える人 |
|---|---|
| 本のタイトル・あらすじ・URL・おすすめポイント | 参加者全員（登録期間の開始以降） |
| 誰が登録したか | 参加者全員 |
| ギフトコード | 登録した本人（常時）と、受け取った人（成立後）のみ |
| その本を何人が希望しているか | 誰にも見えない |
| 誰がどの本を何位で希望したか | 本人だけ。主催者にも見えない（6.8） |
| 誰が誰の本を受け取ったか | 参加者全員（結果公開後） |
| ドラフトの抽選順 | 結果公開後に見せてもよい |

主催者に特権はない。他人のギフトコードは主催者にも見えない。

主催者だけが開ける画面は、主催者以外には 404 を返す。403 だと、招待されていない交換会が実在することを、URL を試すだけで確かめられてしまう。

未ログインのときは 404 ではなくログイン画面へ送る。**このとき、交換会を引く前に送ること。** 引いてから送ると、実在する交換会だけがログイン画面へ、存在しない id は 404 へ分かれ、ログインしないまま id を試すだけで実在を確かめられてしまう。ログインを求める判定が先にあれば、応答は id によらず同じになる。

## 9. 用意すべき状態バリエーション

- 交換会に本が1冊も登録されていない
- 希望リストが空のまま希望提出期間の締切が迫っている
- 自分がまだ1冊も登録していない（受け取る権利がない状態）
- 自分の本が返却された
- 参加者が自分ひとりしかいない
- 期間の締切まで残り数時間
- 登録冊数が1人に偏り、主催者管理画面に警告が出ている（6.8）
- 受け取りが0冊。取得枠が0だった場合と、枠はあったのに回ってこなかった場合の両方（6.5）
- 本が1冊も登録されないまま実行された（6.5 の全体の成立結果が節ごと畳まれる）
- 通知用の Webhook URL が入っている。Discord と Slack の両方の形式
- どこにも参加していない利用者がいる（6.6 の空状態と、6.7 の「これから参加する」）

最後の1つだけは主役として見られない。参加していない人としてしか出ない画面なので、`/dev/login` で入れ替わって見る。

### 9.1 作り方

上の状態は `db/seeds.rb` から `DevelopmentSeeds`（`lib/development_seeds.rb`）が作る。`bin/rails db:seed` で12の交換会と6人の利用者ができ、5つのフェーズと上の項目がすべて揃う。

**development でしか作らない。** production を弾くだけでは足りない。`db:prepare` はデータベースを作ったときに seed も通すため、CI のようにまっさらな test のデータベースを毎回作る環境では、rspec が始まる前にデータができてしまう。件数を数える spec がその分だけずれて落ちる。

- **交換会1つにシナリオ1つ。** 1つの交換会に状態を詰め込むと、片方を見るためにもう片方を崩すことになる
- **何を見るための交換会かは名前が言う。**「登録が偏っている交換会」のように、本らしい題ではなく状態そのものを名前にする。一覧のカードに出るのは名前・フェーズ・主催者・人数・すべきこと・締切までで、概要は出ない（6.6）。名前が本らしい題だと、12枚のカードから目的の1枚を探すのに1枚ずつ開くことになる。名前に入り切らない細部（残り時間、冊数の内訳、Webhook URL の有無）は概要の末尾に「（開発用データ: …）」として書く
- **日時は基準時刻からの相対で決める。** 現在時刻を差し替える仕組みは持たない（11.）。基準時刻は `db/seeds.rb` が入口で1回だけ読み、`DevelopmentSeeds.new(at:)` に渡す
- **二度目以降は日時だけが数え直される。** 招待トークンを決め打ちにしてあるので、`bin/rails db:seed` を繰り返しても交換会は増えず、日時が新しい基準時刻から引き直される。「締切まで残り数時間」は放置すれば次のフェーズへ移るため、見たくなったらもう一度通す。消してから作り直すなら `bin/rails db:seed:replant`
- **主役は「開発たろう」という利用者。** 作ったデータはこの人として見ることを前提に組んであり、12すべてに参加者として入っている。参加していない交換会は一覧に並ばず、画面から辿り着けない
- **主役の名前を「あなた」にはしない。** 交換会一覧は主催者が自分のとき、名前の代わりに「あなた」と書く（6.6）。名前まで「あなた」だと、画面に出た「あなた」が置き換えの結果なのか名前そのものなのかを見分けられず、ギフトコードの注記も「見えるのはあなたと あなた さんだけ」になる。かといって普通の人名にすると、ほかの参加者と見分けが付かない。人名の形を借りつつ、ほかに混ざらない姓にする
- **主役のほかに、どこにも参加していない利用者を1人置く。** 交換会一覧の空状態（6.6）と招待URL着地画面の「これから参加する」（6.7）は、参加していない人としてしか見られない。主役を1つも参加していない状態にすると、ほかの11が全部見られなくなる
- **受け取りが0冊の2つは、どちらも主役が0冊であること。** 言い分けの文面（6.5）は本人にしか出ない。他人として見ても、その画面は出てこない
- **枠はあったのに回ってこない状態には、自分の本の返却が必ず伴う。** 総冊数と総取得枠は必ず等しいので、主役の枠が空いたまま終わるには、余った本が主役のものでなければならない。ほかの人の本が余れば、余り物の割当がその空き枠へ回してしまう。狙って作るときは、主役の本を誰も希望せず、ほかの本がドラフトで出払う形にする。希望リストを互いに重ならないように配るのは、抽選順がどう出ても同じ結果にするため
- **本が1冊も無くてもマッチングは実行できる。** 実行サービスが拒むのは「そのフェーズでは書き込めない」ときだけで、冊数は条件にしていない。割当が1つも作られず、抽選順だけが記録される
- **Webhook URL はホストだけ本物にする。** 送信側（11.）が形式を見分けられるかを手元で試すため。ID とトークンは偽物にしてあり、叩いても 404 が返るだけでどこにも届かない。交換会は URL を1つしか持たないので、Discord と Slack は別々の交換会に入れる
- **どの交換会にも主催者の参加がある**（2. 用語 / 6.9）。DB の制約では守れないので、交換会を作る経路を1つに絞って必ず参加を作る
- **結果公開の割当はマッチング実行サービスを通して作る。** 返却を手で書くと本物と違う形のデータが残る。マッチング実行日時も直接は書かず、実行した結果として記録させる。マッチングは一度だけ実行できるもので、二度目の `db:seed` は実行のやり直しではないため、割当は作り直さない。ただし実行日時だけは新しい基準時刻から引き直す。ほかの日時は毎回引き直されるので、ここだけ据え置くと結果公開の日付が取り残される
- **シナリオを足したら `bin/rails db:seed:replant` を通す。** 本は用意したタイトルを作った順に配るので、途中にシナリオを足すと、それ以降の交換会の割り当てが1つずつずれる。古い開発用データが残ったまま `bin/rails db:seed` を通すと、同じ参加に別のタイトルの本ができ、希望の順位が既存のものとぶつかって落ちる。日時だけが数え直される前提が効くのは、シナリオが変わっていないあいだに限る

作った利用者は Google のアカウントを持たないため、本来の経路ではログインできない。入れ替わりは `/dev/login` から行う（11.）。

## 10. デザイン上の重視点

- **待ち時間の長いツールである。** 登録期間と希望提出期間で数週間かかる。訪れるたびに「今なにをすべきか」がすぐ分かることが、あらゆる装飾より優先される。
- **本を選ぶ楽しさが中心。** おすすめポイントを読み比べる時間が、このツールの一番おいしいところ。一覧はざっと眺められて、気になったものはじっくり読めるとよい。
- **ギフトコードは慎重に。** 一度見えたら取り消せない。伏せ字が既定で、明示的な操作で開く。
- **結果画面は祝祭的に。** ここが交換会のクライマックス。誰から贈られたかが分かり、お礼を言いたくなる作りが望ましい。
- **少人数向け。** 1つの交換会は数人から十数人、1人が参加する交換会は多くても十数件を想定。大規模なデータ表示や高度な検索・絞り込みは不要。絞り込みを持つのは本の一覧の「すべて ／ 自分の本」だけとする（6.2）。
- **過度に堅くしない。** 業務ツールではなく、本好きが集まる遊びの場。ただし読みやすさは犠牲にしない。

**この見積もりに乗っている判断。** 次の判断は、どれも「少人数向け」の見積もりだけを根拠にしている。見積もりが外れれば揃って見直しになるので、根拠はここが1度だけ持つ。各箇所が書くのは前提を名指す一文とここへの参照までとし、崩れる条件も含めて根拠を書き写さない。

- **本の一覧にページングも「もっと見る」も持たない**（6.2）。カードを畳まず全件並べるのも同じ根拠（`decisions/0007`）。崩れるのは、並ぶカードが数十枚に届いて、読み比べの途中で気になった1枚へ戻れなくなったとき
- **結果画面の全体の結果を全件並べる**（`decisions/0009`）。崩れるのは、表から自分の行と、自分が出した本の行き先を目で拾えなくなったとき
- **主催者管理画面の参加者一覧を全件並べる**（`decisions/0008`）。崩れるのは、主催者が未提出の人を目で拾えなくなったとき
- **交換会一覧に絞り込みを置かない**（6.6）。終了した交換会を畳むボタンを置かないのも同じ根拠（`decisions/0010`）。崩れるのは、結果公開のカードが末尾に溜まって、締切を持つものが画面の外へ押し下げられるようになったとき。そのときも、まず当たるのは絞り込みではなく、終了したものを畳むほうになる
- **交換会一覧にいま動いている件数を出さない**（6.6）。崩れるのは、朱のカードが一目に収まらなくなったとき。そのときも、まず当たるのは件数ではなく、朱のものを画面の内に留めるほうになる

**人数そのものは合図にならない。** 「参加者が◯人を超えたら」で見直すのではなく、上に挙げた破綻が1つでも起きたときに見直す。同じ人数でも、1人が何冊出すか、いくつの交換会に参加しているかで、先に破綻する画面が変わる。破綻が出たとき、直すのはその画面でも、残りの判断がまだ通るかはあわせて読み直す。

**規模を根拠に何かを持たないと決めたら、この一覧に1行足す。** 足し忘れると、同じ根拠に乗っているものが1つだけ古い形で残る。判断の経緯は `decisions/0018`。

### 10.1 採用したビジュアル方針

Claude Design の「本の交換会ツールビジュアルガイド」から DIRECTION 2a「見通しを紙の色で」を採る。

- 階層は文字の大きさ・太さ・整列で作る。**影は使わない**
- 色には意味の担当を1つずつ持たせる。朱＝押すものと締切、松葉＝成立と完了、
  それ以外は生成りの濃淡。無彩色ではなく生成りの濃淡なので、密度が高くても硬くなりにくい
- 書体は Zen Kaku Gothic New の1つで通し、太さ 400 / 500 / 700 だけを使う
- 残り時間や冊数は等幅数字（`tnum`）で並べる。桁が変わっても数字がずれない
- 余白は 4px グリッド

配色と書体は `app/assets/tailwind/application.css` の `@theme` にトークンとして置き、
ビューからは `bg-surface` `text-ink` `border-line` のような Tailwind のクラスで参照する。
名前は英語の意味名で持ち、デザイン資料の和名との対応はコメントに残す。
ビューに生の色コードを書かない。

## 11. 技術的な前提

- Web アプリ。デスクトップとモバイル両方で使われる。モバイルからのアクセスが多いと想定
- ログインは OAuth。プロバイダは Google のみとする。想定している利用者が確実に持っている
  アカウントが Google だから。GitHub は持っていない人がいる。顔見知りの少人数グループで使うため、
  ログインできない人が1人でも出るプロバイダは選べない
- 開発とテストの環境に限り、OAuth を通さない裏口ログインを `/dev/login` に置く。seed が作った利用者は
  Google のアカウントを持たず、本来の経路では入れない。5フェーズと状態バリエーション（9.）は
  「誰として見るか」で意味が変わるため、入れ替われないと作ったデータの大半が確かめられない。
  経路はルーティングとコントローラの両方で塞ぐ。ルーティングは起動時に描かれるので production には
  経路そのものが無いが、環境を取り違えて描かれたときでも通さない。
  ログイン画面の末尾に、同じ条件で出し分けたリンクを置く。条件を片方だけ変えると、
  押せば 404 になるリンクが残る。
  OmniAuth の developer strategy は使わない。uid を手で打つことになるうえ、`from_omniauth` が
  ログインのたびにアバターを上書きするので、作った値が消える
- 認証後は元の画面へ戻す。戻り先はサーバーが見たパスだけを覚え、自サイト内に限る。パラメータや Referer から受け取ると、本物のログイン画面を経由したもっともらしいリンクで、認証直後に偽サイトへ落とせる。招待URL着地画面からのログインもこの経路に乗る
- 通知は Discord / Slack の Webhook でチャンネルに投稿する。個人宛の通知はない
- 日時はすべて JST
- 現在時刻を差し替える仕組みは持たない。フェーズは日時から導出されるため、確認したい状況は日時をずらしたデータを用意して作る（9. 用意すべき状態バリエーション）。フェーズ判定は基準時刻を必須の引数で受け取り、締切ちょうどの挙動を spec で突けるようにする。基準時刻はリクエストやジョブの入口で1回だけ読んで回す。読むたびに現在時刻を取ると、締切をまたいだ瞬間に1つの画面の中でフェーズが食い違う
- フェーズが許さない書き込みは 409 Conflict で拒否する。リクエストの形も認可も正しく、交換会の現在のフェーズだけが操作を許していないため。応答には現在のフェーズとできなかった操作を出し、待てば書けるのかどうかが分かるようにする
- 主催者が自分の参加を動かそうとした場合は 403 Forbidden で拒否する。辞退も自分自身の除外も、いつ来ても通らないため。フェーズによる拒否と同じ 409 にすると、待てば抜けられるように読める。判定は役割を先に見る。フェーズを先に見ると、締切後に主催者が押したときだけ理由が入れ替わる
- 希望リストの並べ替えで、送られた集合が現在の希望リストと食い違う場合も 409 Conflict で拒否する。こちらもリクエストの形と認可は正しく、違うのは抜け方だけで、待つのではなく画面を読み直せば通る。403 にすると何をしても通らないように読める
- 乱数シードは bigint で保存する。`Random.new_seed` は 128bit で収まらないため、生成時に 2^62 未満の整数にする
- 招待トークンと乱数シードは交換会の作成時に発行する。招待トークンは URL に載るため 128bit の乱数を URL-safe Base64 で表現する。
  乱数シードは作成後に変更できない。変更できると結果を引き直せてしまう。招待トークンは主催者が再発行できる
- 参加日時は参加レコードの作成時刻を使う。辞退と除外はレコードを消すので、専用のカラムは持たない
- ファイルのアップロードは行わない。参加者のアバターは OAuth プロバイダが返す URL を文字列で持つ。
  本に表紙画像は付けない
- 表示名は本人が入力する。OAuth プロバイダが返す名前は初回ログイン時の初期値としてだけ借り、
  以降はプロバイダ側で改名しても追従しない。追従させると、本人が変えた名前がログインのたびに巻き戻る。
  実名で登録している人が多いプロバイダもあるため、参加者一覧に出す名前は本人が決められる必要がある。
  表示名の重複は許す。顔見知りの少人数で使うため、同名はアバターと本の登録内容で見分けが付く
- メールは送らない。通知は Webhook のみ
- 非同期処理と定期実行は Solid Queue。ワーカーは専用のプロセスを持たず、
  `SOLID_QUEUE_IN_PUMA=true` で Puma の中に立てる。サーバーは1台で、
  Web とジョブの負荷が競合するほどの量は流れない
- ジョブのテーブルは、どの環境でも主のデータベースと分けた別のデータベースに置く。
  主のデータベースに相乗りさせると、交換会のテーブルと同じ `db/schema.rb` に
  ジョブのテーブルが並ぶ。production だけ別という食い違いも残る。
  `DATABASE_URL` は `primary` という名前の設定にしかマージされないため、
  development と test の queue には `config/database.yml` で接続先を明示する
- ジョブの引数は queue のデータベースに平文で残る。ログのフィルタ（`filter_parameters`）は
  ここに効かない。ギフトコードと招待トークンをジョブの引数に渡さない。
  ジョブには本や交換会の id を渡し、必要な値はジョブの中で取り出す
- 開発環境も production と同じ Solid Queue で動かす。Rails 既定の `:async` は
  プロセス内のスレッドで走り、積まれたことも失敗したことも残らないため、
  通知が飛ばなかったときに見るものが無くなる
- 定期実行の定義は development にも置く。定義が拾われたかどうかは
  `solid_queue_recurring_tasks` の行でしか分からず、production にしか定義が無いと
  手元に確かめる足場が無い
- test 環境ではジョブを実行せず、積まれたところで止める（Rails 既定の `:test`）。
  通知の spec が見たいのは「送ろうとしたこと」で、実行まで見たい spec だけが
  明示的に回す。設定ファイルの誤りは起動するまで分からないため、
  `config/queue.yml` と `config/recurring.yml` が読めることは spec で固定する
- Webhook へ投稿するのは Discord と Slack の2つで、どちらの形式かは URL のホストで見分ける。
  交換会は URL を1つしか持たないため、形式を選ばせる項目は置かない。
  対応していないホストと https でない URL には送らない。URL にはトークンが載るので、
  平文で流れる経路には投げない。URL が未設定の交換会にも送らない。
  通知は交換会ごとの任意の設定なので、送り先が無いことは失敗として扱わない
- 通知の送信は1件1ジョブにする。フェーズの変わり目を拾う走査（7.）は交換会を順に見ていくため、
  走査の中で同期的に送ると、1件の Webhook が詰まっている間、後ろの交換会の通知が待たされる。
  リトライも交換会ごとに独立する
- 送信の失敗は、時間をおけば通りうるもの（5xx・429・つながらないとき）と、
  待っても変わらないもの（それ以外の 4xx）に分ける。前者は5回まで積み直し、
  後者は積み直さない。どちらも諦めたときにログへ残す。通知が来ないことに気付いた人が、
  送ろうとして届かなかったのか、そもそも送っていないのかを見分けられるようにする
- 例外のメッセージに Webhook URL を載せない。ホストと HTTP の状態までにする。
  例外はログにもジョブの失敗の行にも残るため、載せた時点でトークンが漏れたことになる
- 送信サービスは渡された本文をそのまま投げ、交換会からは URL 以外を読まない。
  本文にギフトコードを混ぜないのは文面を組む側の責任にする。送信の直前に本文と
  ギフトコードを突き合わせる検査は置かない。照合のために平文の取得経路が
  `Book#gift_code_for` の外にもう1つ増えるほうが危うい（8.）
- フェーズの変わり目は、切り替わる時刻にジョブを予約して拾う。フェーズは日時から導出され状態カラムを
  持たないため、変わった瞬間を知らせてくれるものが無いが、切り替わる時刻は交換会の日時カラム
  そのものなので、そこを直接指せる。定期的に全件を見に回る必要はない。
  Solid Queue のディスパッチャが予約を見ているので、その上に自前の走査を重ねないためでもある
- 予約は交換会の保存に載せる。日時を書き込む経路は作成と編集の2つあるが、どちらも保存を通る。
  経路ごとに積むと、あとから足された経路だけ通知が来ない状態に気付けない
- 予約は取り消さない。主催者が日時を動かしたら、新しい時刻を積み足すだけにする。
  古い予約が残っても、実行時にフェーズを導出して記録と突き合わせるので、空振りするか
  正しい通知を出すかのどちらかにしかならない。予約は「この時刻に確認しに来て」という合図で、
  正しさはジョブの側が持つ。取り消しには queue のデータベースを直に掘ることになる
- 予約を取りこぼした交換会を拾うために、1日1回の走査を別に置く。予約は queue のデータベースに
  しか無く、積み損ねても、ジョブが失敗して止まっても、自分では戻ってこない。走査は状態を
  持たないので、原因が直れば次の回で再開する。入口は2つだが、どちらも同じ判定を通るので
  振る舞いは1つになる
- 最後に知らせたフェーズを交換会に持ち、いまのフェーズと食い違うときだけ投稿する。
  通知履歴のテーブルは持たない。要るのは「同じフェーズを二度出さない」ことだけで、
  履歴を読む画面が無く、行だけが増え続ける
- 本文を組んでから記録を進め、進められたときだけ投稿を積む。予約と走査が重なっても同じフェーズを
  二度出さない。積む前に落ちれば取りこぼすが、チャンネルへの投稿は取りこぼしより重複のほうが困る。
  記録を先に進めると、本文を組む途中で落ちたときにその交換会の変わり目が二度と出ない。
  リンクのホストが未設定のまま動かすとこれが起きる
- ジョブが止まっていた間に複数のフェーズをまたいだ場合、投稿するのはいまのフェーズだけにする。
  飛ばしたフェーズは出さず、記録にも残さない。締切が過ぎた期間の開始を今さら知らせても、
  促す行動がもう無い。予約した時刻ではなく、実際に走った時刻のフェーズを見るのもこのため
- 準備中は投稿せず、記録だけ進める。交換会が作られた直後の状態で、始まりを知らせる変わり目ではない。
  作られた時点で既に登録期間なら、その予約が待たずに走って登録期間の通知が出る。これは変わり目
  ではないが、チャンネルに交換会の存在を知らせる最初の投稿になる
- Webhook URL が未設定の交換会でも記録は進める。進めないと、あとから URL を足したときに
  過ぎた変わり目がまとめて出る
- 結果公開だけは日時では決まらず、主催者がボタンを押したときに起きる。マッチング実行日時も
  予約する時刻として扱い、押された時点ではもう過ぎているので、待たずに走る。
  実行の中で同期的に送る経路は別に作らない。送る判断が2か所に割れる
- 通知の本文は交換会名・新しいフェーズ・次の締切・該当画面へのリンクの4つ。締切の無いフェーズ
  （マッチング実行待ちと結果公開）は締切の行ごと落とす。待っているのが主催者の操作で日時では
  動かないか、もう終わっているためで、締切の名前だけが残った行を出さない。
  リンク先は結果公開だけ結果画面、ほかは交換会ページ
- 通知のリンクは素の URL を1行で置く。Slack は `<url|text>`、Discord は `[text](url)` と記法が割れるが、
  素の URL はどちらもリンクになる。送り先ごとに文面を分けずに済む
- リンクのホストは設定から採る。通知を組むジョブにはリクエストが無い。production は `APP_HOST` から読み、
  既定値は置かない。ホストを取り違えたリンクは、押した人が別のサイトへ飛ぶまで気付けない。
  未設定でも起動は通す。Docker のビルド中に `assets:precompile` が production で走るため
- 締切前のリマインドは、締切の24時間前から締切までの間に1回だけ投稿する。対象は登録の締切と
  希望提出の締切の2つで、準備中・マッチング実行待ち・結果公開には出さない。準備中が待っているのは
  締切ではなく登録期間の開始で、促す行動がまだ無い。ほかの2つは待っているのが主催者の操作か、
  もう終わっている（4.）
- ウィンドウを24時間にするのは、走査の間隔と同じにするため。ウィンドウを24時間より短くすると、予約を
  取りこぼした日に走査がウィンドウの中へ落ちない。24時間ちょうどなら、1日1回の走査が必ず1回だけウィンドウの中に入る。
  段は1つにする。3日前と前日の2段にすると、記録が「どの締切か」では足りず「どの段まで出したか」になる
- **リマインドを出すかどうかは交換会の日時だけから決める。** 誰が登録したか、誰が希望を出したかは
  読まない。人数も名前も本文に含めない。8. の可視性ルールと対になる不変条件にあたり、あとから
  「まだの人が3人います」を足そうとしたときに止める根拠になる
- 「全員が対応済み」は条件として持たない。登録も希望提出も下限（0冊）はあるが上限が無く、
  登録冊数がそのまま取得枠になり（3.）、取得枠より少ない希望しか出していない人は受け取り損ねる（6.2）。
  0冊かどうかで測れるのは「対応済み」ではなく「まったく手を付けていない」だけになる。
  これに伴い、0冊のまま動かない参加者を対象にどう含めるかという論点も消える
- 最後にリマインドを出した締切の時刻を交換会に持ち、いまの締切と食い違うときだけ投稿する。
  フェーズ名では記録しない。登録期間のうちに主催者が締切を先へずらしても「登録期間は出し済み」の
  まま残り、新しい締切のリマインドが出なくなる。通知履歴のテーブルを持たないのはフェーズの
  変わり目と同じ理由による
- リマインドの予約も交換会の保存に載せ、締切の24時間前を積む。フェーズの変わり目とは予約を分ける。
  予約する時刻が締切そのものではなく、そこからウィンドウの分だけ手前になるため。1つにまとめると、
  どちらの都合で引き算しているのかが読めなくなる。どの日時が締切にあたるかは交換会が答え、
  何時間前に知らせるかはリマインドの側が持つ
- リマインドの本文は交換会名・締切が近いこと・締切・交換会ページへのリンクの4つ。
  リンク先はフェーズによらず交換会ページにする。促したいのは登録か希望の提出で、
  どちらもその画面にある
- spec が本物の Webhook を叩かないよう、登録していない外部通信は webmock ですべて落とす。
  送信サービスを差し替えられるようにするだけでは、そこを通らない経路が残る

上記により、Rails 標準のうち Active Storage / Action Mailer / Action Mailbox / Action Text は使わない。
`config/application.rb` で railtie ごと読み込まない。必要になった時点で戻す。
