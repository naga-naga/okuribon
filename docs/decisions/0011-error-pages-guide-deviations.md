# 0011 エラー画面でビジュアルガイドから採らなかったもの

- 日付：2026-08-21（この記録に集めた日。各項目を決めたのは #133 の時点）
- 発端：#182（元は `docs/spec.md` 10.2「ガイドから採らなかったもの」）

## 決めたこと

エラー画面（6.10、ガイドの `エラー画面.dc.html`）について、
資料の描き方を以下の13点で採らない。
資料は9区画あるが、実装が採るのは 01 / 02 / 05 / 08 / 09 だけになる。

## 項目

### 参加していない交換会の 403 画面

**決めたこと** — 持たない。404 を返し、**文言も存在しない交換会と同じにする**（6.10）

**なぜ** — 8. が正面から反対している。403 だと、招待されていない交換会が実在することを
URL を試すだけで確かめられてしまう。ステータスだけ揃えても、片方にしか
当てはまらない文面を出せば、そこから実在が読める

**却下した代替案** — 04 は「存在は認めるが中身は出さない」と見出しに書き、
「この交換会には参加していません」と返す画面を描く

### 401「ログインの有効期限が切れました」

**決めたこと** — 持たない

**なぜ** — 8. は未ログインを 404 でもエラー画面でもなくログイン画面へ送ると決めており
（しかも交換会を引く前に送る）、専用の画面を足すと同じ状況に応答が2つできる。
資料が添える「書きかけの内容は下書きとして残っています」は、下書きの仕組みが
無いので果たせない。「さきほど見ていたページに戻ります」のほうは
11. の戻り先の仕組みがそのまま果たしている

**却下した代替案** — 04 の右の枚がこの画面を描く

### 招待URLが使えない画面

**決めたこと** — 期限切れは 6.7 招待URL着地画面の一状態として扱い、
そちらが概要と日程を見せたまま理由を書く。無効なトークンは素の 404 を返す

**なぜ** — 左の「期限を過ぎています」は交換会名を出しており、トークンが引けている
状態にあたる。これはエラーではない。右の「無効になっています」については、
トークンが正しくないことと交換会が無いことを区別しない（`InvitationsController`）

**却下した代替案** — 03 の2枚が、どちらも専用のエラー画面として描かれている

### マッチングが失敗した主催者向けの画面

**決めたこと** — 持たない

**なぜ** — この状態がそもそも起きない。希望を出さなかった人には最後に余った本が
ランダムに割り当てられる（3.）ので、割当が決まらないことはない。資料が添える
「期間を延ばす」はマッチングを一度だけ実行できる決めごと（3.）と両立せず、
「希望の重なりを見る」は 8. の「誰がどの本を何位で希望したかは本人だけ。
主催者にも見えない」に反する

**却下した代替案** — 07 の右がこの画面を描く

### 503 メンテナンス

**決めたこと** — 持たない

**なぜ** — デプロイ中の画面は 8. デプロイ（#56）の持ち場にあたる。加えて資料の
「進行中の交換会の締切は、点検の時間だけ後ろにずれます」は果たせない。
フェーズは日時カラムから導出するだけで、点検の時間を差し引く仕組みが無い（4.）

**却下した代替案** — 07 の左がこの画面を描く

### 500 のエラーIDとコピー

**決めたこと** — 置かない

**なぜ** — 控えを出す仕組みが無い。加えて資料の宛先が「続く場合は、この控えを
主催者に伝えてください」で、宛先そのものが違う。主催者は交換会を立てた
参加者であって、この道具の管理者ではない。伝えられても何もできない

**却下した代替案** — 02 は「ERR-5031 / 2026-08-14 21:04」を控えとして出す

### 404 の「交換会が主催者によって削除された可能性があります」

**決めたこと** — 「URL が間違っているか、招待を受けていないページです」で通す

**なぜ** — 交換会を削除する口が無い（`config/routes.rb` の `resources :exchanges` に
`destroy` は無い）。起きないことを原因として挙げない

**却下した代替案** — 資料は削除された可能性を原因として挙げる

### 404 の「トップページ」

**決めたこと** — 持たない。押せるものは1つに絞り、ログイン中は交換会一覧、
未ログインはログイン画面へ送る

**なぜ** — 行き先にあたるサービストップを持たないと決めた（5.）。
この2つがそれぞれの人にとってのトップページにあたるので、
副の口を足すと主ボタンと同じ画面を指す口が隣に並ぶ

**却下した代替案** — 01 と 08 は主ボタンの隣にこの副の口を置く

### エラー画面の簡易ヘッダー

**決めたこと** — 4xx では共通ヘッダーをそのまま通す。
簡易な帯を採るのは 500 と 406 だけにする（6.10）

**なぜ** — 全画面でログアウトを持つことが共通ヘッダーを入れた第一の理由（#81）で、
行き止まりの画面でこそ効く。500 と 406 は DB もセッションも読めない前提から
簡易な帯にせざるを得ず、資料の帯がその2枚とちょうど噛み合う

**却下した代替案** — 01 / 02 / 03 / 08 はどれも「■ ＋ サービス名」だけの帯を描き、
ログアウトの口を持たない

### 画面を捨てないエラー（インライン）

**決めたこと** — #133 では入れない

**なぜ** — この issue が揃えるのは全画面のエラーで、06 は希望リストの保存経路
そのものに手を入れることになる。オフラインの検知も接続が戻ったときの自動保存も
実装が持たないため、枠だけ先に置いても果たせない。入力の不備を項目の直下に
出すこと自体は既存のフォームがすでにそうしている

**却下した代替案** — 06 は保存失敗・オフライン・入力の不備をインラインで描く

### 拒否の画面の次の一手が2つあること

**決めたこと** — 「交換会ページへ」の1つにする

**なぜ** — #136 の統合で、資料が指していた2つの行き先は同じ交換会ページになった。
同じ場所を指す口を2つ並べても選べない

**却下した代替案** — 05 は「希望リストを並べる」と「登録した本を見る」を並べる

### 406 の画面

**決めたこと** — 01 の組み立て（控えの数字 → 見出し → 一文）だけを借り、
組み方は flex も grid も使わない素朴なものに落とす

**参照できるもの** — 資料に対応する絵が無い。エラー画面の9区画はどれも
ブラウザが CSS を読める前提で描かれている。参照できるものが無かったので、
採否ではなく補いにあたる

### 400 の画面

**決めたこと** — 404 / 422 と同じ型で1枚用意する

**なぜ** — `params.expect` を通る口が多く、実際に届きうる

**参照できるもの** — 資料に対応する絵が無い。これも採否ではなく補いにあたる

## 影響する場所

- `app/views/errors/show.html.erb` / `denied.html.erb`
- `public/500.html` / `public/406-unsupported-browser.html`
- `app/controllers/invitations_controller.rb`
