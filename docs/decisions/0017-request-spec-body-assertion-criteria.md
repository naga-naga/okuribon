# 0017 request spec で response.body を検証してよい条件を決める

- 日付：2026-08-21
- 発端：issue #177

## 決めたこと

`response.body` の検証は、落ちたときに直すべきものが実装である場合に限る。
残す条件と落とす条件は `CLAUDE.md`「テスト > request spec と画面の文言」に書いた。

決めた基準で既存の request spec を見直し、次にあたる検証を落とした。

- 文言の出現回数（「必須」の印がちょうど2回、日時入力欄が3つ）
- `index` の大小で見る画面部品の並び（フォームの項目順、カード内の段の順、
  フェーズ帯〜本の一覧の縦の並び）
- 状態によらず常に出る固定文言（プレースホルダ、並び順の説明、主催の目安、
  進み方の3段の説明文）と、出さないと決めた装飾が出ないことだけを見る検証
- 書体と配色の読み込み

## なぜ

request spec の `response.body` への検証が約300箇所あり、文言や見た目を少し変える
だけでテストが落ちる一方、何を保証しているのか読み取りにくいものが混ざっていた。

分けたのは「文言そのものが仕様なもの」と「たまたまの文言に乗っただけのもの」。
前者（可視性、実在の秘匿、拒否の理由、出し分けの言い分け）は文言が変わったら
実装を疑うべきで、検証が落ちるのが正しい。後者はテンプレートの書きぶりで、
落ちても spec を書き換えて追従するだけになる。その保証はビジュアルガイドと
レビューが持つ。

## 却下した代替案

- **文言の検証をすべて `I18n.t` で組む。** 文言変更には追従するが、キーが正しく
  引かれていることしか保証しなくなる。実在を伏せる 404 では、参加していない場合と
  存在しない場合でキーが分かれた時点で、検証が通ったまま文面が割れる。
  素の文字列か、応答どうしの突き合わせで書くことに意味がある
- **見た目の構造も request spec で持ち続ける。** 並び・印の個数・書体は資料
  （ビジュアルガイド）が描いており、変えるたびに落ちる spec は資料の写しになる。
  写しは元を直したときに一斉に古くなる
- **見た目の検証をブラウザ経由のテスト（system spec）へ移す。** 移す先を新設する
  ほどの保証ではない。Stimulus との接続（data 属性やフレームの宛先）は挙動なので、
  これまでどおり request spec が持つ

## 影響する場所

- `CLAUDE.md`「テスト > request spec と画面の文言」
- `spec/requests/` 全体
