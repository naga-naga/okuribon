# 0015 1冊だけを開く画面を持たず、ギフトコードの置き場を結果画面に寄せる

- 日付：2026-08-21（この記録に集めた日。決めたのは 2026-08-08、PR #99）
- 発端：#183（元は `docs/spec.md` 6.3 に織り込まれていた経緯）

## 決めたこと

- 1冊だけを開く画面は作らない（6.3）
- ギフトコードを読む口は、登録期間中の編集フォーム（6.4）と結果画面（6.5）の2つとする
- 結果画面には、受け取った本のコードに加えて、返却された自分の本のコードも置く（6.5）

## なぜ

#23（本の詳細を作る）に着手する前に、この画面にしか無い情報を数えたところ
1つも残らなかった。タイトル・登録者名・おすすめポイント・あらすじ・ストアへのリンクは
6.2 のカードが全文を持っていて、開けばその場で読める。

ギフトコードだけは置き場所に迷った。8. が「登録した本人（常時）」と書いているため、
登録期間を過ぎてからも本人が読める画面が要るように見える。実際には要らない。
コードを読みたくなる場面は登録期間中（入力の確かめ）か結果公開後（受け取った本を使う、
返却された自分の本を使う、相手から使えないと言われて確かめる）のどちらかで、
その間の希望提出期間とマッチング実行待ちには、コードを読んでできることが無い。
8. は**誰に見せてよいか**の規則であって、どのフェーズにも表示画面を置けという要求ではない。

代わりに 6.5 へ、返却された自分の本のコードも開けるよう条件を足した。
誰にも渡らなかったコードの取り出し口が、詳細画面を落とすと他に無くなるため。

## 却下した代替案

- **本人だけが自分の本のコードを読める画面を別に置く** — 8. の「常時」を画面の数として
  読んだ場合の形。読んでできることが無いフェーズのために画面が1枚増える
- **一覧にコードを載せて代わりにする** — カードが十数枚並ぶ画面で開かせることになり、
  肩越しに1枚も覗かれずに済ませるのが難しい。可視性の判定を一覧側に持つことにもなる（8.）

## 影響する場所

- `docs/spec.md` 5. / 6.2 / 6.3 / 6.5
- `config/routes.rb` と `app/controllers/books_controller.rb`（`show` を持たない）
- ビジュアルガイドの採否は 0005 にある（「本の詳細画面そのもの」）
