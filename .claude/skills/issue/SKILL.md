# issue に着手して PR を出す

task issue 1件を1つの PR に対応させる。以下を順に行う。

## 1. 読む

```
gh issue view <番号>
```

task issue は「やること / 完了条件 / 参考」で構成される。**完了条件がそのまま受け入れ基準**なので、
ここを箇条書きのまま控えておき、最後に1つずつ照合する。

続けて次を読む。読まずに実装を始めない。

- 親 Epic — `gh issue view <番号> --json parent --jq '.parent.number'` で番号が取れる。
  Epic の「完了の定義」「前提」に、task issue には書かれていない制約があることが多い。
  **前提を読み、着手できる状態かを確かめる**
- `docs/spec.md` の該当節 — issue の「参考」に節番号が書かれている
- `CLAUDE.md` の厳守事項のうち、この issue に関わるもの

Epic の「前提」に未完了の issue が挙がっていたら、着手前に指摘する。

## 2. 方針を合意する

スキーマを変更する、新しい抽象を導入する、複数の既存ファイルにまたがる、のいずれかに当たるなら、
方針を短く説明して合意を取ってから書き始める。単一ファイルに閉じる小さな変更なら省略してよい。

## 3. ブランチを切る

main が最新であることを確かめてから切る。

```
git switch main && git pull
git switch -c <issue番号>-<英小文字ケバブの要約>
```

## 4. TDD で実装する

完了条件を TODO リストに落とし、1つずつ Red → Green → Refactor で進める。

1. **Red** — 失敗する spec を書き、実行して**意図した理由で**落ちることを確かめる
2. **Green** — 最短で通す。この段階は汚くてよい
3. **Refactor** — 重複を除き設計を整える。spec を通し続けながら進める

一度に複数の TODO を並行させない。Red を見ないまま実装を書き始めない。

- スキーマの変更は必ずマイグレーションで行う
- ビジネスロジックはモデルとサービスに置き、コントローラは薄く保つ
- コメントは日本語で書く

## 5. 不変条件を確認する

`invariants` skill を実行する。ギフトコードの可視性、サーバー側のフェーズ検証、
乱数シードとマッチングの一回性、現在時刻の取得経路の4点を、差分に対して確認する。

## 6. 検証する

```
bin/rubocop -a
bin/rspec
bin/ci
```

`bin/ci` にテストは含まれないため `bin/rspec` を別に走らせる。
落ちたら直す。落ちたまま次へ進まない。

## 7. コミットする

規約は `CLAUDE.md`「コミットメッセージ」に従う。要点は3つ。

- 差分から読み取れない意図を書く。何を変えたかではなく、なぜそうしたか
- PR は squash されず、各コミットが main の履歴に残る。1コミット1目的にする
- **Red の状態をコミットしない。** Red → Green → Refactor は1コミットにまとめ、
  そのコミット単体で `bin/rspec` が通るようにする

コミット前に `git log` で直近のメッセージを読み、書きぶりを揃える。

## 8. PR を出す

```
gh pr create
```

タイトルと本文は日本語。本文には次を含める。

- この PR で何を解決したか
- `closes #<issue番号>`
- 完了条件のうち、満たしていないものがあればその理由

push には確認を求められる。

## 9. 報告する

完了条件を1つずつ照合し、満たしたもの・満たしていないものを明示する。
実装中に仕様書にない判断をしたなら、`docs/spec.md` に書き足したかを確認する。

issue は PR のマージ時に `closes #N` で閉じ、Epic の進捗は sub-issues が自動で集計する。
マージ後の手作業はない。
