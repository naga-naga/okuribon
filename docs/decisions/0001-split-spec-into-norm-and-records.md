# 0001 spec.md を規範と記録に分ける

- 日付：2026-08-20
- 発端：#176

## 決めたこと

- `docs/spec.md` は唯一の規範として維持する。書くのは実装を縛る決まりと、
  それを短く支える理由まで
- 節番号 1.〜11. は動かさない。コード内約45箇所のコメントと skill が節番号で
  参照しており、番号の安定が参照の前提になっている
- 判断の経緯と却下した代替案は `docs/decisions/` に1件1ファイルで積む
- 10.2 の「ガイドから採らなかったもの」（約400行）は decisions へ移す（#182）。
  10.2 に残すのはガイドと画面の対応表だけ
- 6.x に織り込まれた経緯の段落も decisions へ寄せる（#183）

## なぜ

spec.md は1239行あり、大半が「その時そう判断した」記録でありながら
「こうあるべき」という規範の形で書かれていた。もともと Web 版 Claude での
検討を Claude Code へ持ち込むための資料だった経緯による。規範と記録が
同じ調子で混ざっていると、守るべき決まりと単なる経緯を読み分けられず、
記録が増えるたびに仕様書が同じ調子のまま肥大する。

記録そのものは捨てない。10.2 が言うとおり、書き残さないと次に同じ画面を
触るときに、差が意図的なものか見落としかを判別できない。

## 却下した代替案

- **維持** — 混合を明文化するだけでは、肥大と読み分けの問題がそのまま残る。
  この issue が立った理由が解けない
- **縮小** — 記録の性格が強い部分を削るだけだと、記録の置き場が無くなる。
  git 履歴と issue は時系列の置き場で、「その画面を触るときに引く」形をしていない
- **廃止** — 規範の置き場が別に要る。ギフトコードの可視性やフェーズ検証は
  複数ファイルにまたがる不変条件で、コードコメントには集約できない。
  `CLAUDE.md` は Claude への指示書で、人が読む仕様書の代わりにならない。
  コード内45箇所と skill の参照をすべて引っ越すコストにも見合わない

先にコメントの一斉見直し（#168）で spec への参照を減らしてから決める案も
検討したが、採らなかった。#168 の「節番号参照を残すか」は spec.md の形が
決まらないと決められず、参照を消すこと自体が廃止を裏口で選ぶことになる。
残すコメントの基準を「コードに書けない理由だけ」とするなら、spec 参照の
多くは残す側に落ちるため、先にやっても参照は大して減らない。

## 影響する場所

- `docs/spec.md` — 冒頭に規範と記録の分担を明記。10.2 の積み先を decisions へ変更
- `CLAUDE.md` — 「仕様」「ビジュアルガイド」「作業の進め方」の記述を分担に合わせた
- `.claude/skills/issue/SKILL.md` — 採らなかった判断の積み先を decisions へ変更
- #160 と #168 はこの決定を前提に着手できる
